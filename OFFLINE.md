# Поставка без интернета и GPU

В корне проекта находится `package_offline.sh`. Он **не запускает и не обновляет
рабочий стенд**: собирает образы на машине с интернетом и создаёт один архив для
Linux/amd64. Другие архитектуры не заявляются. Распознавание речи в этой поставке
отключено: ASR-модель не нужна и в архив не включается.

## Упаковка

Нужны Docker с Compose, Git, Bash, curl, flock (util-linux) и обычные Linux-утилиты.
При первом запуске скрипт сам скачивает Qwen3.5-9B Q4_K_M (5,7 ГБ) из
[репозитория Unsloth на Hugging Face](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF/blob/3885219b6810b007914f3a7950a8d1b469d598a5/Qwen3.5-9B-Q4_K_M.gguf)
в `models/Qwen3.5-9B-Q4_K_M.gguf`. Версия закреплена; размер и SHA-256 проверяются
перед сборкой. При обрыве сети повторный запуск продолжает загрузку из `.part`.
Готовые веса используются повторно. Веса, временный файл и файл блокировки
исключены из Git через `.gitignore`: на GitHub отправляются только скрипты.
Классификатор берётся из уже подготовленного `models/classifier`.

```bash
# Скачать Qwen (если его ещё нет), собрать образы и упаковать всё:
./package_offline.sh

./package_offline.sh \
  --version release-1 \
  --work-dir /srv/tmp \
  --output /srv/export/simulator112.tar.gz
```

`--llm-model /srv/models/custom.gguf` позволяет использовать свой готовый
однофайловый GGUF без скачивания. Аналогично работает `DDS_LLM_MODEL_PATH`.
При отсутствии явно указанного файла скрипт останавливается, не подменяя модель.
`--no-download` запрещает загрузку весов. `--check` ничего не скачивает и не
собирает: проверяет наличие весов и готовность Docker. Если Qwen ещё не скачан,
эта проверка сообщит об отсутствующем файле.

Нужно место под образы, копии весов и итоговый сжатый архив одновременно.
Сборка использует текущие отслеживаемые Git файлы, включая их незакоммиченные
правки. Новый исходник, ещё не добавленный в Git, в контекст не попадёт.
Локальные секреты и рабочие данные туда не копируются. Веса классификатора могут
быть локальными: необходимые известные файлы копируются явно.

В поставку входят четыре образа, веса, CPU Compose без секции `build` и GPU,
контрольные суммы, установка, запуск/остановка, проверка, backup/restore и README.
Backend и frontend собираются, PostgreSQL и официальный CPU llama.cpp скачиваются
на машине упаковки, затем все четыре образа сохраняются `docker image save`.
Для воспроизводимого переноса сохраняются именно эти образы и их ID, а не только
ссылки на обновляемые внешние теги.

## Перенос уже наполненной базы

Добавьте `--with-data --source-project 112-simulator-core`. Это экспортирует
PostgreSQL и `/app/data` из существующих контейнеров, не останавливая их. Учебную
работу на время экспорта следует прекратить, чтобы файлы соответствовали снимку
БД. Архив будет содержать реальные учётные записи и материалы; храните его как
резервную копию. Текущие `.env` и TLS-ключи в него не добавляются.

## Установка на закрытом сервере

Нужен установленный Docker Engine с Compose. Python, Node, PostgreSQL, GPU,
CUDA и NVIDIA Container Toolkit на хосте не нужны.

```bash
tar -xzf simulator112.tar.gz
cd simulator112-offline
./install.sh             # чистая установка
# либо ./install.sh --restore — для поставки с экспортом БД и файлов
```

Установщик создаёт `.env` с новыми секретами и паролем первого администратора.
Для восстановленных аккаунтов сохраняются прежние пароли. Данные живут в томах
Docker и переживают замену контейнеров. Образы загружаются из архива; скачивания и
сборка на сервере запрещены. Backend доступен через Nginx; БД и LLM наружу не
публикуются. Для HTTPS из локальной сети подготовьте сертификат нужного адреса,
доверенный браузерами курсантов.

`verify.sh` ждёт готовности backend, интерфейса и LLM, затем выполняет
синтетическую генерацию без реальных занятий. Наличие собранного архива само по
себе не подтверждает скорость и работоспособность выбранной модели на сервере.

**Ограничение исходного приложения:** синтез речи сейчас отключён, а legacy TTS
зависит от отдельного сервиса. Скрипт не выдаёт его за работающий. Уже имеющийся
аудиокэш переносится с `--with-data`, доступные веса TTS — если присутствуют.
Генератор текстовых реплик подключается к общему CPU LLM через новые настройки
`FACTOIDS_LLM_BASE_URL/MODEL/TIMEOUT_SECONDS`; значения по умолчанию в разработке
сохраняют прежний адрес Ollama.

## Проверка самого упаковщика

```bash
python3 -m unittest discover -s scripts/tests -p test_offline_packaging.py -v
```

15 проверок используют записывающие имитации Docker и загрузчика: комплектность архива и
контрольных сумм, отсутствие секретов, перенос данных только по флагу, корректную
архитектуру, отказ при ошибке сборки/отсутствии моделей/повреждении весов, повторную
установку без смены паролей и отказ восстановления поверх существующей БД.
Также проверяются загрузка и повторное использование весов, продолжение после
обрыва, отказ при повреждении, исключение весов из Git и запрет загрузки в `--check`.
Это не тест реального inference. Проверки упаковщика добавлены в Quality Gate.
Отдельно прошли 5 адресных pytest-проверок маршрутизации LLM, прежнего генератора
и сохранности frontend ДДС; проверены Compose и входящий HTTP-доступ через две
сети на временном контейнере.

Полная сборка комплекта с весами и запуск реальной модели на момент разработки
не выполнялись: многогигабайтная загрузка в ходе разработки не запускалась.
В дополнительном старом `tests/test_api.py` остаются два ожидания 200 вместо 403;
те же падения воспроизведены на исходном main `22def95`, права доступа не менялись.
