# Проверка и восстановление резервных копий

`python -m scripts.backup_db` создаёт атомарно публикуемый backup: PostgreSQL — `.sql` через `pg_dump` 15, SQLite — `.db` через online backup API с учётом WAL. Пароль в диагностике маскируется. По умолчанию каталог `data/backups`, в Compose — named volume `/app/data/backups`; `BACKUP_DIR` позволяет выбрать приватный каталог.

Перед восстановлением остановите **все пишущие клиенты**, сохраните исходную БД, проверьте версию, целостность, права и свободное место. Сначала восстановите в новую отдельную БД и проверьте пользователей/число записей/связи/вход, затем переключите сервис. Не импортируйте дамп поверх заполненной рабочей БД.

PostgreSQL: создайте отдельную пустую БД и исполните `psql -X -v ON_ERROR_STOP=1 -U <user> -d <new_database> < backup.sql` внутри контролируемой среды. Не помещайте пароль в историю команд; используйте приватный `.pgpass`/секрет среды. Для Compose дамп читается из `/app/data/backups` backend-контейнера; скопируйте нужный файл в приватный каталог командой `docker cp` после проверки имени контейнера. На целевом PostgreSQL должны существовать роли, нужные дампу. Переключение требует изменения `POSTGRES_DB`/конфигурации и перезапуска backend/backup sidecar.

SQLite: при остановленном приложении скопируйте проверенный `.db` в **новый путь**, выполните `PRAGMA integrity_check`, установите права пользователя backend и задайте новый `DATABASE_URL`. Не оставляйте WAL/SHM от другой базы по целевому имени. Учтите, что файлы uploads/модели/TLS/.env в снимок БД не входят и резервируются отдельно. Потеря SECRET_KEY инвалидирует токены; пароль DB и ключ подписи не публикуйте вместе с открытым отчётом.

Проверяемый изолированный restore PostgreSQL 15:

```bash
docker build -t simulator_backend:latest -f Dockerfile.backend .
BACKEND_IMAGE=simulator_backend:latest bash scripts/test_pg_backup_restore.sh
```

Скрипт проверяет наличие image **до** выделения ресурсов, создаёт собственные сеть/PG/временный каталог, использует backup-код из image, восстанавливает другую БД, сравнивает Unicode имена, число и сумму записей, затем удаляет свои ресурсы. Он не доказывает восстановимость конкретного рабочего дампа; проводите такой drill с реальными копиями и фиксируйте RPO/RTO. Не запускайте очистку чужих volumes. Sidecar retention удаляет только файлы формата, создаваемого нашим backup-кодом.
