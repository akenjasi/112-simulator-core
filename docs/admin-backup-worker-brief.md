# Задание Gemini: исправить ручное резервное копирование БД

Проект: `/home/cidralitr/uni/hakaton-arseni/112-simulator-core`.
Исполнитель: Gemini 3.8 Flash High в Antigravity.

## Цель и соответствие ТЗ

Восстановить работающий сценарий администратора: создать резервную копию БД,
после обновления страницы найти её среди сохранённых копий и скачать файл.
Проверить восстановление в отдельном тестовом окружении.

Это ограниченный этап требования «проводить резервное копирование данных».
Список и скачивание — минимальные средства использования созданных копий.
Не считаем этот этап реализацией отдельного требования «настраивать параметры
резервного копирования». Расписание, срок хранения и выбор каталога в UI не нужны.
Не называй результат «полной копией системы»: копируется только БД, без uploads,
аудиозаписей на диске, моделей, сертификатов и конфигурации. Укажи границы в UI
и финальном отчёте; не заявляй полное покрытие всех данных комплекса.

## Подтверждённая причина текущей ошибки

Codex проверил запущенный Docker-комплекс 17 октября 2026:

- `POST /api/admin/backup` отвечает 500;
- в traceback: `FileNotFoundError: [Errno 2] No such file or directory: 'pg_dump'`;
- `pg_dump` отсутствует в backend-контейнере;
- сервер PostgreSQL: 15.19;
- Dockerfile.backend не устанавливает клиент резервного копирования PostgreSQL.

Не маскируй отсутствие pg_dump успешным mock-ответом или пустым файлом.
Добавь в образ совместимый клиент и проверь **реальное** создание и восстановление
дампа PostgreSQL 15. Наличие исполняемого файла само по себе не является приёмкой.
По возможности сохрани кэш тяжёлого слоя Python/torch при изменении Dockerfile.

## Требуемое поведение

### Создание копии

1. Сохранить `POST /api/admin/backup` и `/backup/`, auth только ADMIN,
   совместимые поля ответа `backup_file` и `status`. Дополнительные поля допустимы.
2. PostgreSQL: реально создавать дамп настроенной БД существующим subprocess
   механизмом, без блокировки event loop. Не подменять БД SQLite при ошибке.
3. SQLite остаётся поддержанным, поскольку уже есть в проекте и тестах:
   использовать согласованный SQLite backup API, а не простое копирование файла,
   которое может пропустить WAL. Не создавать пустую исходную БД и не выбирать
   другую БД, если настроенный источник отсутствует.
4. Данные сохранять в существующий постоянный `data/backups` (`/app/data/backups`
   в Docker). Уникальные имена: два запроса в одну секунду не перезаписывают файл.
5. Писать во временный файл; окончательное имя публиковать только после успеха.
   При ошибке/таймауте удалять только временный файл текущей операции, старые копии
   сохранять. Незавершённые файлы не попадают в список/скачивание.
6. Ограничить время subprocess (например, 120 секунд с константой, которую можно
   уменьшить в тесте); при таймауте завершать и ожидать дочерний процесс.
7. Успешный ответ — только при успешном завершении и наличии непустого файла.
   Это необходимая проверка создания, но не доказательство возможности восстановления:
   последнее проверяется отдельным интеграционным тестом.
8. Ошибки отсутствия утилиты, отказа pg_dump, записи файла и таймаута дают non-2xx
   и понятный безопасный `detail`. Не отдавать клиенту пароли, DATABASE_URL,
   сырые команды и stderr. В технические логи также не писать credentials.

### Постоянный список и скачивание

1. Использовать существующий `GET /api/admin/backups`, сохранив обёртку `backups`.
   Убрать заглушку, добавить серверную проверку ADMIN. Не регистрировать дубликат
   маршрута с неопределённым порядком разрешения.
2. Источник списка — успешно сохранённые файлы, а не состояние браузера. Для каждой
   записи: безопасное имя/идентификатор, дата UTC с часовым поясом, размер в байтах.
   Сортировка новые первыми, устойчивый порядок при одинаковом времени.
   Простой обход существующего каталога достаточен; отдельная БД заданий не нужна.
3. Добавить `GET /api/admin/backups/{filename}/download` с ADMIN-only FileResponse
   и корректным Content-Disposition. В filename только имя файла, не путь.
4. Список/скачивание не раскрывают абсолютные пути сервера, не принимают `../`,
   абсолютные/URL-encoded traversal, каталоги или symlink, ведущие за backup_dir.
   Не отдавать любые произвольные файлы из data. Только допустимые завершённые
   копии поддерживаемых форматов. Не менять имена и не удалять старые копии.
5. Несуществующая/недопустимая копия — 404 либо согласованный 4xx,
   а не 500. Без авторизации — 401, TEACHER/CADET — 403 на create/list/download.

### Frontend

1. На существующей странице `/admin/system` заменить историю текущей сессии
   реальным списком с сервера. Новую страницу/пункт меню не создавать.
2. Показать имя, дату в локальном времени, размер и кнопку «Скачать».
   Кнопка обновления списка, загрузка, пустой список, ошибка и повтор.
3. После создания обновлять список; после перезагрузки копия остаётся видна.
   Различать «копия создана, но список не обновился» и ошибку самого создания.
4. Скачивать с существующими auth headers через fetch/blob; не передавать токен
   в URL. Корректно освобождать object URL после скачивания.
   При ошибке скачивания показывать сообщение, не сохранять JSON ошибки как файл.
5. Обе существующие кнопки создания (дашборд и system) должны показывать безопасное
   объяснение ошибки из API, не только «500». Повторный клик во время создания
   блокируется, после неудачи повтор доступен.
6. Отображать именно «Резервная копия базы данных», без обещания полного бэкапа
   комплекса. Не менять остальную диагностику, графики и журнал администратора.

## Границы изменений

Разрешены `Dockerfile.backend`, `scripts/backup_db.py`, backup-часть router_admin
и схем admin, минимальные изменения legacy backups в main.py, admin-api и
backup-блоки двух существующих admin страниц; новые профильные тесты и точечное
обновление старых backup-тестов.

Не входят: восстановление рабочей БД кнопкой/API, расписание, retention/удаление,
настройки пути хранения, облачное хранилище, полный архив файлов комплекса,
новый сервис/очередь, миграции БД, переделка аудита и политик, посторонние ошибки
типов, изменения зависимостей Python/Node и lockfiles. docker-compose.yml не менять
без доказанной необходимости: текущий `/app/data` уже постоянный.

Сохрани существующие несвязанные изменения. Не коммить, не пушь. Не выполняй
`compose down -v`, очистку volumes/images, изменение рабочей БД или восстановление
в неё. Реализация и тестовая сборка разрешены; рабочие контейнеры не перезапускать
и не пересобирать рабочее развёртывание до отдельной команды пользователя.
Не устанавливай утилиту только в запущенный контейнер: исправление должно быть
воспроизводимо из Dockerfile. Дополнительные воркеры допустимы для непересекающихся
подзадач; итоговую интеграцию и проверки ведёт основной исполнитель.
