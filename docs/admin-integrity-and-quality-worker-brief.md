## 3. Ручной контроль целостности файлов backend

### Назначение и границы

Обнаруживать изменение/исчезновение выбранных файлов backend относительно
эталона текущей Docker-сборки. Это базовый контроль случайных изменений;
эталон находится в том же образе и не защищён независимо от владельца контейнера.
В UI писать «Целостность файлов backend», не «Вся система защищена/исправна».

Не входят: файлы frontend в другом контейнере, БД, uploads, аудио, логи, бэкапы,
секреты/.env, сертификаты, зависимости site-packages, большие GGUF-модели,
противодействие администратору хоста, подпись сборок, автоматическое исправление.

### Эталон

- Добавь небольшой генератор manifest и модуль проверки. Используй SHA-256
  и чтение файлов блоками, не загружай бинарники целиком в память.
- Зафиксируй область контроля: Python-файлы приложения в backend, startup-скрипт
  scripts/init.sh, checker/generator и native-компоненты transcribe-cli, qwen-tts
  и необходимые поставляемые с ними shared libraries. Явно исключи модели,
  __pycache__, кэш, данные и изменяемые каталоги.
- Существуют symlink native-библиотек: изучи их и выбери явную политику контроля
  ссылки/целевого файла. Не выходить за разрешённый root, не пропускать все
  библиотеки молча и не обходить рекурсивно внешние symlink.
- Генерируй manifest в Dockerfile.backend **после** всех операций COPY/chmod/sed,
  меняющих контролируемые файлы. Сборка должна падать, если обязательный файл
  отсутствует/не читается. Runtime не генерирует эталон заново.
- Manifest содержит версию формата, явную область, относительные пути, контрольные
  суммы и при необходимости размер. Сам manifest не должен хешировать себя.
  Для идентификации эталона можно использовать digest его байтов; не требуй .git
  внутри образа и не добавляй новую систему релизов.
- Неверный формат/hash, повторяющиеся/абсолютные пути, выход через .., пустой
  manifest или отсутствие обязательных записей — ошибка эталона, а не успех.

### API и интерфейс

- Добавь ADMIN-only `POST /api/admin/integrity/check`. Используй штатную авторизацию:
  anonymous 401, TEACHER/CADET 403, активный ADMIN разрешён.
- Проверка работает read-only, не меняет файлы и эталон. Хеширование выполнять
  вне event loop. Не принимать произвольные root/пути от пользователя.
- Результат различает: всё совпало, выявлены отклонения, проверка недоступна.
  Для отклонений укажи относительный путь и причину (изменён/отсутствует/не читается).
  Нечитаемый/повреждённый эталон никогда не превращается в зелёный результат.
- Верни время проверки UTC, digest эталона, область, число проверенных файлов,
  список отклонений. Не возвращать содержимое файлов и абсолютные пути сервера.
- Проверять только объявленные области/наборы. Если обнаруживаешь дополнительные
  файлы, называй это отклонением только в явно контролируемой области, а не во
  всём /app. Состав исключений и политика дополнительных файлов должны быть
  одинаковы у генератора и checker и отражены в тестах/отчёте.
- На существующей `/admin/system` добавь компактный блок с ручной кнопкой,
  областью контроля, временем и результатом последней проверки и отклонениями.
  До запуска — «Проверка не выполнялась»; не показывать зелёный заранее.
- Кнопка блокируется на время запроса. Ошибка понятна, повтор доступен.
  Нет нового пункта меню, polling, фонового расписания и отдельного сервиса.
- Запуск уже фиксируется общим middleware. Добавь отдельное осмысленное audit
  событие завершения (actor, время, результат/числа отклонений) штатным механизмом;
  не выдавай generic POST-запись за результат проверки. Содержимое файлов не логировать.
- Не добавляй кнопку «Принять текущее состояние за эталон» и endpoint обновления
  manifest. Штатное обновление приложения приносит новый эталон вместе с образом.
- В локальной dev-среде без manifest показывать понятную недоступность проверки,
  не формировать эталон молча и не утверждать, что всё совпало.

## Тесты и приёмка

Типы/существующее поведение:

- Корректные обработчики и подсказки операторской панели, SMS остаётся недоступной.
- Tutorial запускается; завершение/пропуск вызывает onFinish согласно текущему API.
- Закрытие WebSocket активного звонка допускает reconnect; отбой до срабатывания
  таймера и unmount отменяют reconnect. Fake timers, без настоящих звонков.
- Оба теста live-страницы загружают реальный существующий компонент.
- Дашборд: до ответа нет демонстрационных CPU/RAM/точек; после ответа реальные
  значения; сбой обновления виден и не добавляет фиктивную точку истории.

Контроль целостности — новые backend и frontend acceptance tests:

1. Эталон и исходные файлы совпадают — успех.
2. Изменённый и удалённый файл обнаруживаются с правильным путём/причиной.
3. Изменение исключённого кэша/логов/данных не даёт ложного нарушения.
4. Отсутствующий, повреждённый, пустой, небезопасный manifest не даёт успеха;
   тесты traversal и выбранной политики symlink.
5. API права доступа, корректный ответ и осмысленное audit-событие результата.
6. UI первоначальное состояние, ожидание, совпадение, отклонения, ошибка и повтор.
7. **Отдельный собранный тестовый контейнер**: нетронутый образ проходит; изменить
   контролируемый неисполняемый fixture/файл в одноразовой копии контейнера —
   нарушение; удаление — нарушение. Рабочие контейнеры не изменять.
8. Проверить, что manifest сформирован после изменений файлов при сборке и новый
   образ не наследует эталон старого. Не генерировать эталон в начале проверки
   для получения проходящего теста.
