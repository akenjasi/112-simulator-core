# Задание Gemini: журнал действий пользователей и системных ошибок

Проект: `/home/cidralitr/uni/hakaton-arseni/112-simulator-core`.
Модель: Gemini 3.8 Flash High в Antigravity.

Реализуй первую версию журнала для администратора по требованиям ниже.
При необходимости можешь привлечь дополнительных воркеров с непересекающимися
задачами. Ты отвечаешь за итоговую интеграцию и проверку их изменений.
Не коммить, не пушь, не разворачивай приложение и не меняй credentials.

## Цель

Администратор должен из интерфейса просматривать уже записанные действия
пользователей и системные ошибки, находить записи по периоду и пользователю,
открывать подробности. Данные реальные, из БД, сохраняются после перезагрузки.
Это первая версия просмотра существующих журналов, а не полный аудит всех
событий комплекса и не сбор логов Docker/ОС.

Важные факты:

- `GET /api/admin/audit-logs` уже возвращает **массив** записей действий,
  поддерживает limit/offset и ограничен ADMIN.
- `UserActionLog`: log_id, timestamp, user_id, role, action, endpoint,
  target_entity, target_id, ip_address, details. action_type — alias action.
- `SystemErrorLog`: id, timestamp, error_message, traceback. Пользователя,
  статуса HTTP и компонента в этой модели нет.
- Общий middleware пишет действие **до** выполнения запроса. Нельзя представлять
  такую запись как подтверждение успешного действия. Специализированные события
  уже могут содержать дополнительные сведения в action/details.
- Некоторые поля у старых записей пустые, details может быть JSON или обычным текстом.
- Legacy `/api/admin/audit` вызывает функцию get_audit_logs напрямую. При изменении
  её сигнатуры не сломай этот вызов и не оставляй обход ADMIN-проверки через alias.

## Интерфейс

Добавь `/admin/logs` и пункт «Журналы» в общее меню администратора
(через adminNavItems, чтобы работали desktop и mobile).
Используй существующие компоненты и стиль панели, русские подписи.

Две вкладки:

1. «Действия пользователей»:
   - таблица: дата/время, пользователь, роль, действие;
   - имя пользователя из безопасного серверного JOIN или существующего admin users
     API; user_id — устойчивый идентификатор для фильтра;
   - при отсутствии имени показывай user_id, при отсутствии user_id —
     «Не указан». Не заменяй историческую роль текущей ролью пользователя;
   - в подробностях: ID записи, время, пользователь, роль, action,
     endpoint, объект/ID объекта, IP, details — только имеющиеся поля.
2. «Ошибки»:
   - таблица: дата/время и сообщение об ошибке;
   - подробности: ID записи, время, полное сообщение, traceback при наличии;
   - не приписывай ошибке пользователя или причину, которых нет в записи.

Общее поведение:

- Новые записи первыми; стабильная сортировка timestamp DESC, затем ID DESC.
- Фильтр периода «С» / «По» на обеих вкладках; пользователь — только на вкладке
  действий. Можно заполнить одну границу или обе. Есть сброс фильтров.
- Время показывать по локальному часовому поясу браузера, обозначив это в UI;
  запросы отправлять с явным часовым поясом, а не наивной строкой локального времени.
- Пагинация на сервере, по 20 записей; кнопки «Назад» / «Далее».
  Для определения следующей страницы можно запрашивать 21 запись, показывать 20,
  увеличивать offset на 20. Не загружать весь журнал для фильтрации в браузере.
- При смене вкладки/фильтров сбрасывать страницу на первую. Применение периода —
  кнопкой «Применить», неправильный период показывать до запроса.
- Кнопка «Обновить» повторяет запрос с текущими фильтрами и страницей.
  Автообновление и live-stream в первую версию не включать.
- Различать загрузку, пустой журнал/пустую выборку и ошибку загрузки с повтором.
  Ошибку запроса нельзя показывать как «Записей нет».
- Старый ответ не должен перезаписывать новую выборку при быстрой смене вкладки,
  периода или страницы. Используй отмену и/или защиту от устаревших ответов.
- Подробности доступны кнопкой с понятной подписью; закрываются кнопкой и Escape.
  Длинные сообщения не ломают мобильную вёрстку.
- details с валидным JSON можно форматировать. Невалидный JSON показывать текстом.
  Сообщения и traceback отображать как текст, без интерпретации HTML.
- Не добавлять колонку «Успешно/Ошибка», если результат не записан в источнике.
  Коротко объяснить в интерфейсе, что журнал действий не всегда подтверждает
  успешное выполнение запроса.

## API и совместимость

- Сохрани `GET /api/admin/audit-logs` и его массив в ответе, limit/offset и
  существующие поля. Дополнительные поля допустимы, удаление/переименование — нет.
- Расширь его необязательными query-параметрами `from_at`, `to_at`, `user_id`.
- Добавь `GET /api/admin/error-logs` с массивом записей ошибок, limit/offset,
  from_at/to_at и типизированной response schema.
- Обе границы периода включительные. API принимает ISO datetime с явным UTC/offset,
  нормализует в UTC для сравнения; даты без часового пояса и from_at > to_at — 422.
  Учитывай поведение SQLite и PostgreSQL, включая старые timestamps из SQLite.
- Фильтры применяются в SQL **до** limit/offset. limit 1..1000, offset >= 0.
- Все новые и затронутые маршруты просмотра, включая legacy alias аудита:
  без авторизации — 401, TEACHER/CADET — 403, активный ADMIN — доступ разрешён.
  Не полагайся только на скрытый пункт меню.
- Используй существующие auth headers на frontend, включая fallback ключей токена.
- Не меняй формат существующего PDF-отчёта и другие API.
- Не создавай production endpoint для искусственного вызова ошибок.

## Тесты — написать до реализации и затем добиться прохождения

Создай `tests/test_admin_journal.py` и
`frontend_react/tests/admin_journal.test.tsx`.
Проверяй наблюдаемое поведение, не внутреннее устройство функций.

Backend:

1. ADMIN получает обе выборки и подробности записей; TEACHER, CADET и anonymous
   не получают их. Отдельно проверить legacy alias аудита на те же ограничения.
2. Новые первыми; одинаковое время не делает порядок неопределённым.
3. Фильтры по одной/двум границам, другой UTC offset с тем же моментом времени,
   точное попадание в границу, пользователь и сочетание фильтров.
4. limit/offset применяются после фильтрации, последовательные страницы без повторов
   для неизменного набора записей; пустая выборка — 200 и [].
5. Неверные даты, наивные даты, обратный период, limit/offset вне границ — 422.
6. Старый контракт audit-logs без новых параметров остаётся совместимым.
7. Nullable поля, отсутствующее имя пользователя, простой текст и JSON в details.
   При добавлении JOIN не терять записи без пользователя.

Frontend:

1. Навигация на страницу, вкладки, реальные ответы API, загрузка и пустое состояние.
2. Период/пользователь передаются в запрос; сброс, пагинация и обновление работают;
   первая страница при изменении фильтров, у последней нет активной «Далее».
3. Открытие/закрытие подробностей, полный текст ошибки/traceback, nullable поля,
   JSON и не-JSON details, HTML-подобная строка остаётся текстом.
4. Ошибка загрузки отличается от пустого списка, доступен повтор.
5. Задержавшийся старый ответ не меняет актуальную вкладку/выборку.
6. Токен передаётся штатным helper, пункты журнала доступны в обоих меню.
7. Нет придуманного успешного результата и пользователя у системной ошибки.

Запускай backend-тесты **только с отдельной временной тестовой БД**:
существующие fixtures могут удалять таблицы. Не использовать рабочую БД из .env

Если проект требует другой Python environment, используй существующее окружение
без обновления зависимостей. Сначала проверь, что приложение не подменяет явно
заданный DATABASE_URL рабочим значением.
