# Архитектура и интеграция пользовательского интерфейса цикла занятий ДДС (FRONTEND А-06)

## 1. Обзор архитектуры

Данный документ описывает клиентскую архитектуру и логику интеграции полного цикла групповых и индивидуальных занятий для роли **«Диспетчер ДДС»** (ЕКП 112) в рамках подсистемы А-06.

Интерфейс спроектирован с соблюдением принципов строгой валидации данных, отказоустойчивости сетевых мутаций, изоляции демонстрационного и экзаменационного режимов, а также честного отображения оценок и статусов без клиентской генерации фиктивных данных.

---

## 2. Модуль `lib/dds-cycle.ts`

Модуль предоставляет строгие TypeScript-интерфейсы, валидаторы времени выполнения (runtime validators) и методы обращения к API с поддержкой `AbortSignal` и авторизационных заголовков.

### Валидация состояния (`validateDDSSessionState`)
- **Идентичность сессии:** Проверяет совпадение `session_id` с ожидаемым `expectedSessionId` и `ticket_id` с ожидаемым `expectedTicketId` (без утечки сырых идентификаторов в сообщениях об ошибках).
- **Обязательные панели:** Проверяет наличие всех панелей объекта `incoming_card`: `phones`, `incident`, `caller`, `statuses`, `emergency`, `classification`, `services` (с валидацией массива истории).
- **Строгая проверка баллов:** Допустимы исключительно `null` или конечные числа в диапазоне от `0` до `100`. Строки, булевы значения, `NaN`, `Infinity` и числа вне интервала вызывают отказ валидации.
- **Безопасные сообщения:** При ошибках HTTP API helper возвращает предсказуемые сообщения по коду ответа (401, 403, 404, 409, 500) без трансляции недоверенных сырых полей с бэкенда.

## 3. Компоненты курсанта

### 3.1. `components/dispatcher/dds-assignments.tsx` (`<DDSAssignments />`)
- Запрашивает личный список назначенных занятий курсанта через `GET /api/dds/assignments`.
- Управляет жизненным циклом запроса через `AbortController` и `epochRef`, игнорируя сетевые ответы при размонтировании компонента.
- Отображает номер происшествия, описание, статус прохождения (`Выполнено` при наличии `submitted_at`, `Не завершено` при завершении без отправки) и текущий балл (или `Нет оценки`).
- Генерирует ссылки `/dds/journal?session_id=...&ticket_id=...` с корректным URL-кодированием параметров.
- При ошибке выводит контейнер с `role="alert"` и кнопкой повторной загрузки.

### 3.2. `components/dispatcher/dds-assigned-console.tsx` (`<DDSAssignedConsole />`)
- Главный рабочий пульт диспетчера ДДС для назначенной сессии.
- **Входящие данные:** Использует существующие компоненты `<TopBar>`, `<CallerPanel>`, `<IncidentPanel>` в режиме только чтения входящей карточки.
- **Собственные отметки:** Компактная панель для фиксации действий по службам:
  - Выбор службы (`label="Служба"`).
  - Выбор статуса службы (`label="Статус службы"`), номер наряда, комментарий и сохранение статуса (`POST /api/dds/sessions/{id}/actions` с `kind: "status"`).
  - Направление вызова: поля «Кто принял», «Суть сообщения» и сохранение направления (`kind: "dispatch"`).
- **Журнал действий:** Хронологический список подтверждённых сервером отметок с временем, службой, нарядом и комментариями.
- **Завершение занятия:** Кнопка «Завершить выполнение» (`POST /api/dds/sessions/{id}/finish`).
- **Сетевая надёжность и защита от гонок:**
  - `isSavingRef` защищает от повторных кликов (double click lock).
  - Каждая мутация получает идемпотентный `request_id = crypto.randomUUID()`.
  - При возникновении сетевой ошибки payload сохраняется в `pendingPayloadRef`, блокируя запуск новых мутаций до явного решения: нажатия «Повторить сохранение» (с тем же `request_id`) или ручного обновления состояния с сервера («Обновить»).
  - Смена `sessionId` или размонтирование прерывает текущий запрос через `controller.abort()`, сбрасывает счётчик эпохи (`epochRef`) и очищает старое состояние (защита A→B→A).

## 4. Маршрутизация курсанта

### 4.1. `app/dds/page.tsx`
- Выделен чистый route boundary:
  - При наличии `session_id` монтируется `<DDSAssignedConsole sessionId={...} ticketId={...} />`. Эффекты и хуки старого тренажера не запускаются.
  - При наличии только `ticket_id` без `session_id` выводится уведомление о необходимости открыть назначенное занятие (прямой доступ к билету в обход назначения запрещен).
  - При отсутствии параметров запускается изолированный `<DdsDemoSimulator />` (демонстрационный режим без привязки к назначениям).

### 4.2. `app/dds/journal/page.tsx`
- При наличии `session_id` запускается отдельный дочерний компонент `<AssignedDDSJournal />`, обращающийся к реальному состоянию сессии через `fetchDDSSessionState` и выводящий карточку, историю действий и ссылку на рабочий пульт. Изолирован от демо-данных `INITIAL_INCIDENTS` и ссылок оператора 112.
- Без параметров в начале страницы выводится список назначенных занятий `<DDSAssignments />`, а ниже — демонстрационный журнал.

### 4.3. `app/student/lobby/page.tsx`
- Список назначенных занятий ДДС (`<DDSAssignments />`) интегрирован в основное лобби курсанта.
- Кнопка свободного запуска помечена как отдельный демонстрационный запуск.
- Статичный баннер ожидания заменён нейтральным текстом с рекомендацией открыть назначенное занятие из списка выше либо использовать отдельный демонстрационный запуск ниже.

## 5. Преподавательский контур

### 5.1. Создание урока (`app/teacher/sessions/new/page.tsx`)
- При выборе роли «Диспетчер ДДС»:
  - Отображается выбор подготовленного билета (`/api/dds/tickets`), обязательный для создания занятия.
  - Категории происшествий и адаптивный режим исключаются.
  - Поле лимита ошибок (`error_limit`) отключается и не передается в запросе (оценивание не зависит от штрафов).
  - При получении 404 от `/api/v1/lessons` fallback на устаревший эндпоинт `/api/v1/sessions` для ДДС заблокирован.

### 5.2. Live-мониторинг (`app/teacher/sessions/live/page.tsx`)
- Все запросы (`fetchStats`, `handleStartLesson`, `handleStopLesson`, `handleSaveNotes`) выполняются с заголовком `Authorization: Bearer <token>`.
- Идентификатор сессии считывается напрямую из query-параметра без эвристик `startsWith("sess-")`.
- Монотонный request sequence (`sequenceRef`) и сохранение активного контроллера (`activeControllerRef.abort()`) гарантируют, что ответ на повторное «Обновить» или параллельный poll не перезапишет более свежие данные. Сброс состояния выполняется строго при смене `sessionId`.
- Устранена генерация фиктивных билетов (`tList.push(...)`).
- Статусы курсантов и билетов отображаются на основе реальных данных: `COMPLETED` -> «Выполнено», `INCOMPLETE` -> «Не завершено», `PASSED` -> «Сдано», `FAILED` -> «Провалено», `ungraded` -> «Выполнено, нет оценки», отсутствие баллов -> «Нет оценки».
- Прогресс сессии (`overall_progress`) и число сценариев в процессе (`total_in_progress`) берутся строго из серверных данных без ложного принудительного округления до 100% при остановке урока.
- Исключены синтетические утверждения о присутствии онлайн («В сети» заменено нейтральным статусом «Участник занятия» или «Нет данных об активности»), а списки билетов озаглавлены как «Назначенные билеты». Блок ожидания урока нейтрально сообщает о количестве назначенных участников без ложных утверждений о подключении курсантов.

### 5.3. Аналитика и журнал (`app/teacher/analytics/page.tsx`)
- Запросы истории уроков и заметок преподавателя используют `Authorization: Bearer <token>`.
- Для каждого билета отображается фактический `card_id` и встроенный журнал зафиксированных действий (`t.actions` с полями времени, службы, наряда, принявшего лица и комментариев).
- Статус билета `ungraded` явно отображается как «Выполнено, нет оценки» без ложного приравнивания к `Passed` и без отображения сырого английского идентификатора.
- Отсутствие оценки отображается как «Оценивание не производилось (нет оценки)» и не подменяется ложным бейджем «Ошибок не обнаружено».
- Компонент отчёта А-05 (`DDSLessonReport`) сохранен без изменений.
