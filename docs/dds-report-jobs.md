# Фоновые задания нейроотчётов ДДС (Задача А-04)

## Обзор и назначение

Компонент обеспечивает защищённое асинхронное создание, выполнение и хранение результатов генерации аналитических нейроотчётов по завершённым учебным занятиям диспетчеров ДДС (`DISPATCHER_DDS`).

Построен поверх:
- **А-02** (`backend/core/dds_report_data.py`): сбор и заморозка проверенных исторических данных завершённого занятия;
- **А-03** (`backend/core/dds_report_llm.py`): локальный инференс модели Qwen через OpenAI-compatible API llama.cpp.

---

## Архитектурные ограничения

> [!IMPORTANT]
> **Ограничение текущей версии: один процесс backend (Single Backend Process Constraint)**.
> Фоновый исполнитель `DDSReportJobWorker` работает как выделенный in-process воркер внутри жизненного цикла FastAPI (`lifespan`).
> Без внешнего распределённого брокера сообщений (Redis, Celery, RabbitMQ) и распределённых блокировок запуск нескольких параллельных процессов/реплик backend для фоновой генерации не поддерживается.

## API Контракт

### 1. `POST /api/ai-analytics/lessons/{lesson_id}/report`

Создаёт новое фоновое задание или возвращает состояние/результат существующего.

- **Тело запроса**: Необязательный JSON `{"retry": false}` (допускается пустое тело, `{}` или `{"retry": true}`).
- **Авторизация**:
  - `ADMIN` — полный доступ к любому занятию.
  - `TEACHER` — доступ только к своим занятиям (`Assignment.assigned_by == current_user.user_id`).
  - `CADET` или неавторизованные пользователи — `403 Forbidden` / `401 Unauthorized`.
  - Несуществующее занятие — `404 Not Found`.
  - Занятие не `COMPLETED` или роль не `DISPATCHER_DDS` — `409 Conflict`.
  - *Проверка прав и статуса занятия выполняется до любых операций с заданиями и до вызова LLM*.

- **Поведение и коды ответа**:
  - Нет задания: формируется снимок данных (А-02), создаётся задание со статусом `pending`, ставится в очередь исполнения. **Возвращает `202 Accepted`**.
  - Задание в статусе `pending` или `running`: возвращает текущее задание. **Возвращает `202 Accepted`**. (Повторный запуск не производится).
  - Задание в статусе `completed`: возвращает готовый результат. **Возвращает `200 OK`**. (Повторный запуск не производится даже при `retry: true`).
  - Задание в статусе `failed`:
    - При `retry: false` (или отсутствии поля): **возвращает `409 Conflict`**.
    - При `retry: true`: замораживает свежий снимок данных, инкрементирует `attempt`, сбрасывает статус в `pending`, очищает ошибку и ставит задание в очередь. **Возвращает `202 Accepted`**.

### 2. `GET /api/ai-analytics/lessons/{lesson_id}/report`

Получает сохранённое задание или готовый результат.

- **Поведение и коды ответа**:
  - Задание существует (`pending`, `running`, `completed` или `failed`): **возвращает `200 OK`**.
  - Задание для занятия ещё не создавалось: **возвращает `404 Not Found`**.
  - Идемпотентно: повторное чтение никогда не перезапускает LLM и не генерирует текст заново.

### 3. Формат ответа (`DDSReportJobResponse`)

```json
{
  "job_id": "c1f72a91-4567-4e89-b883-fae20f135b1c",
  "lesson_id": "assignment-uuid",
  "status": "completed",
  "attempt": 1,
  "created_at": "2026-10-17T02:45:00Z",
  "updated_at": "2026-10-17T02:45:10Z",
  "report_text": "Краткий аналитический отчет...",
  "error_code": null,
  "model_used": "dds-qwen"
}
```

**Инварианты полей**:
- `report_text`: возвращается строкой **только** при `status == "completed"` (в остальных случаях `null`).
- `error_code`: возвращается строкой **только** при `status == "failed"` (в остальных случаях `null`).
- `model_used`: имя использованной модели (`nullable`).
- `snapshot`: сохраняется в базе данных, но **никогда не выдаётся** в ответе API задания.

## Модель данных (`dds_report_jobs`)

Таблица создаётся автоматически через общую метадату SQLAlchemy (`Base.metadata.create_all`).

| Колонка | Тип | Описание |
|---|---|---|
| `job_id` | String (PK) | UUID идентификатор задания |
| `lesson_id` | String (Unique, Index) | Уникальный ID занятия (одна запись на занятие) |
| `status` | String | `pending` / `running` / `completed` / `failed` |
| `attempt` | Integer | Номер попытки (начиная с 1) |
| `created_at` | DateTime(timezone=True) | Время создания |
| `updated_at` | DateTime(timezone=True) | Время последнего обновления |
| `report_text` | Text (nullable) | Сгенерированный текст отчёта |
| `error_code` | String (nullable) | Стандартизированный код ошибки |
| `error_message` | Text (nullable) | Санитизированное понятное сообщение об ошибке |
| `model_used` | String (nullable) | Идентификатор модели |
| `snapshot` | JSON (nullable) | Замороженный снимок данных занятия на момент попытки |

### Атомарность, токен попытки и защита от гонок:
- `lesson_id` имеет ограничение `UNIQUE`: параллельные POST-запросы на создание обрабатываются через перехват `IntegrityError` с откатом и возвратом победившей записи (с семантикой 200/202/409).
- **Атомарный захват воркером**: выполняется через SQL `UPDATE dds_report_jobs SET status = 'running' WHERE job_id = :id AND status = 'pending'` (через `RETURNING` либо проверку `rowcount == 1`). Только один победивший поток переводит задание в `running` и генерирует отчёт; параллельные вызовы не запускают повторных генераций.
- **Токен попытки (`attempt token`)**: при захвате фиксируется номер попытки. Все последующие записи завершения (`completed`), ошибки (`failed`) и прерывания (`interrupted`) обусловлены совпадением `job_id`, зафиксированного `attempt` и статуса `running`. Устаревшая попытка не может перезаписать состояние более новой.
- **Атомарный повтор (`retry`)**: выполняется с обязательным сравнением как статуса (`status = 'failed'`), так и зафиксированной попытки (`attempt = observed_attempt`). После обновления состояние ORM обновляется через `populate_existing`, возвращая фактический статус.
- **Дедупликация очереди**: повторные POST-запросы для уже находящихся в очереди `pending`/`running` заданий не дублируют записи в очереди `submit()`.

## Фоновый исполнитель и жизненный цикл

### Изоляция сессий БД:
- Во время сетевого обращения к LLM (`generate_dds_lesson_report`) соединение и транзакция с БД **не удерживаются**.
- Захват задания и чтение снимка выполняются в короткой сессии с немедленным `commit`.
- Запись результата или ошибки выполняется в отдельной короткой сессии после завершения вызова модели.

### Обработка перезапуска и сбоев:
- **При старте приложения (`lifespan start`)**: все задания из предыдущего процесса в статусах `pending` и `running` автоматически переводятся в `failed` с `error_code = "interrupted"` и сообщением о перезапуске сервера. Сохранённые `completed` задания остаются нетронутыми. При возникновении ошибки восстановления старт сервера аварийно прерывается (не запускается с невосстановленными заданиями).
- **При плановой остановке (`lifespan stop`)**: активные задачи исполнителя завершаются, текущее выполняемое задание помечается как `failed` с `error_code = "interrupted"`.
- Завершение воркера и очистка пула соединений (`engine.dispose()`) гарантированно выполняются в блоке `finally` после `yield`.
- Завершение с ошибкой, сетевой сбой или прерывание процесса никогда не создают фиктивный `completed`.

## Стандартизированные коды ошибок (`error_code`)

Все ошибки санитизируются: в ответ и логи не попадают пароли, токены, внутренние URL со служебными данными, дампы снимка и личные данные курсантов:

| Код ошибки | Причина возникновения |
|---|---|
| `interrupted` | Задание прервано перезапуском или остановкой сервера backend |
| `length_exceeded` | Модель превысила лимит токенов генерации (`finish_reason='length'`) |
| `empty_response` | Модель вернула пустой текст или ответ без вариантов (`choices`) |
| `insufficient_data` | В снимке нет завершённых сессий или отсутствуют результаты оценок и билетов |
| `input_too_large` | Снимок данных превышает установленный лимит символов входа |
| `llm_timeout` | Истекло время ожидания ответа сервера инференса |
| `llm_unavailable` | Сервер нейросетевого инференса недоступен / сбой соединения |
| `llm_error` | Сервер инференса вернул HTTP 5xx или невалидный JSON |
| `configuration_error` | Некорректная конфигурация адреса или параметров инференса |
| `generation_failed` | Общая ошибка генерации нейроотчёта |

## Настройка и запуск

Настройки локального инференса описаны в [dds-qwen-runtime.md](dds-qwen-runtime.md).
Процесс backend должен получить `DDS_LLM_BASE_URL`, `DDS_LLM_MODEL` и остальные
параметры А-03 из своего окружения. Env-файл Compose загружает настройки только
для соответствующего Compose-проекта. Для backend на хосте адрес по умолчанию —
`http://127.0.0.1:8081/v1`; внутри контейнера нужен адрес доступного ему локального
runtime (loopback контейнера не является адресом хоста).

Worker запускается автоматически в FastAPI lifespan. Используйте один процесс
Uvicorn и одну реплику backend. Таблица добавляется при штатном старте через
`create_all`; старые таблицы и оценки не изменяются. PostgreSQL 15 и SQLite с
поддержкой `UPDATE RETURNING` (SQLite >= 3.35) поддержаны целевыми проверками.

Новое API пока не подключено к кабинету преподавателя. Старые endpoints
`/trigger` и прежний `ai_worker` остаются отдельным механизмом с заглушкой;
для реального отчёта занятия используйте новые POST/GET `/lessons/{id}/report`.

## Проверка текста преподавателем

Сохранение `completed` означает успешное получение и запись ответа локальной
модели, а не подтверждённую достоверность всех формулировок. Код А-04 не
пересчитывает оценки и не проверяет фактические утверждения свободного текста.
В синтетической проверке 17.10.2026 Qwen написала «в обеих сессиях» при одной
сессии с двумя оценками. Качество текста в этой проверке не принято; преподаватель
должен сверять рекомендации с исходными фактами. Проверка качества модели и
интерфейс преподавателя требуют отдельного этапа.

## Целевая проверка А-04

Для запуска только новых проверок из корня проекта:

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 TESTING=true \
DATABASE_URL=sqlite+aiosqlite:////tmp/imba-a04-tests.sqlite \
SECRET_KEY=local-test-only \
python3 -m pytest -q tests/test_dds_report_jobs_acceptance.py tests/test_dds_report_jobs_unit.py
```

Нужны установленные зависимости backend и pytest. Используйте отдельную тестовую
БД; этот набор создаёт таблицы и синтетические записи. Полный целевой набор также
включает проверки А-02/А-03 и аналитики/авторизации из команды в
[dds-qwen-runtime.md](dds-qwen-runtime.md). Для повторного полного прогона нужна
новая БД: существующие auth-тесты используют постоянные usernames. При проверке
PostgreSQL использован тестовый `NullPool`, чтобы не переносить asyncpg-соединения
между event loop разных тестов; runtime-конфигурация пула не менялась.
