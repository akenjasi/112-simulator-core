# Нейроотчёт занятия в кабинете преподавателя (А-05)

## 1. Какую проблему решили

Ранее преподаватель в журнале истории уроков (`/teacher/analytics`) видел только сводные статистические показатели и детализацию оценок по билетам. Фоновое API нейроанализа ДДС, созданное на этапе А-04 (POST/GET `/api/ai-analytics/lessons/{lesson_id}/report`), не имело пользовательского интерфейса в кабинете преподавателя.

В рамках задачи А-05 реализован клиентский интерфейс для безопасного запуска генерации, отслеживания прогресса и отображения готового нейроотчёта по завершённым занятиям направления «Диспетчер ДДС».

---

## 2. Что изменилось в поведении

1. **История занятий в кабинете преподавателя (`/teacher/analytics`):**
   - В раскрывающейся карточке урока со статусом `COMPLETED` и ролью `DISPATCHER_DDS` монтируется компонент `DDSLessonReport` с `lessonId`.
   - Для уроков с другими статусами (`ACTIVE`, `WAITING`) или целевой ролью `OPERATOR_112` компонент не монтируется.

2. **Загрузка и сохранение состояния:**
   - При раскрытии карточки отправляется `GET /api/ai-analytics/lessons/{lessonId}/report`.
   - Если сервер возвращает `404 Not Found`, фиксируется статус `not_started` («Нейроотчёт ещё не сформирован») с кнопкой запуска. Автоматическая генерация без клика пользователя **запрещена**.
   - Если отчёт уже сгенерирован (`completed`), он сразу отображается из базы данных без повторного запуска.

3. **Синхронная защита от повторных кликов и обработка ошибок POST:**
   - Для предотвращения повторных POST-запросов используется синхронный ref-замок (`isPostingRef`), блокирующий повторный вызов в том же тике до обновления React-состояния `isSubmitting`.
   - Кнопка блокируется визуально (`disabled`), предотвращая двойной клик.
   - Ошибки POST (409, 500, сетевой сбой) переводят компонент в статус `error` с безопасным сообщением и кнопкой «Попробовать снова» («Обновить»), не оставляя компонент в `not_started`. Сообщение 409 предлагает перечитать состояние через «Обновить», а явный retry становится доступным только после того, как `GET` вернёт статус `failed`.

4. **Строгая валидация данных ответа API:**
   - Все ответы (`200`, `202`) валидируются функцией `validateReportPayload`:
     * Обязательно наличие `lesson_id` и его строгое совпадение с запрошенным занятием (`data.lesson_id === requestedLessonId`); отсутствие, `null` или чужой id отклоняются безопасной ошибкой;
     * Статус проверяется по белому списку: `pending`, `running`, `completed`, `failed`;
     * Для статуса `completed` обязательно наличие непустой строки `report_text`.
     * Любой некорректный, неполный или чужой ответ переводит компонент в безопасную ошибку, **никогда** не сбрасывает в `not_started` и не отображает чужой текст.
     * Только реальный HTTP `404` означает `not_started`.

5. **Жизненный цикл, изоляция поколений (Scope Generation) и AbortController:**
   - Все асинхронные запросы (GET, POST, polling) отслеживаются с монотонно возрастающим счетчиком поколений (`scopeGenRef`).
   - При смене `lessonId` (включая сценарий `A -> B -> A`):
     * Предыдущий `AbortController` немедленно отменяется;
     * Активный таймер опроса очищается;
     * Состояния (`report`, `jobStatus`, `isLoading`, `isSubmitting`, `pollingError`) сбрасываются в исходные;
     * Запоздалый ответ от первого `A` гарантированно отбрасывается по несовпадению поколения (`scopeGen !== currentGen`).
   - Ошибка отмены (`AbortError`) никогда не отображается как сетевой сбой.

6. **Последовательный опрос (Polling) и ручное обновление:**
   - При статусах `pending` или `running` компонент опрашивает статус раз в 2 секунды.
   - Опрос строго последовательный: следующий таймер запускается только после завершения предыдущего запроса.
   - Кнопка «Обновить» отменяет активный запрос, очищает очередь опроса и выполняет сериализованный запрос за актуальным состоянием.
   - Временный сбой при опросе не сбрасывает состояние в `not_started` и не вызывает повторный POST.

7. **Безопасное отображение результата:**
   - Текст отчёта выводится как безопасный текст с сохранением переносов (`whitespace-pre-wrap`), без `dangerouslySetInnerHTML` и сторонних библиотек.
   - Отображаются метаданные (модель, дата) и заметное предупреждение:
     > **«Сформировано ИИ. Проверьте выводы по исходным данным занятия»**
     > *Текст подготовлен языковой моделью на основе протокола занятия. Результаты носят рекомендательный характер.*

8. **Авторизация и явный повтор (Retry):**
   - Все запросы используют `getStoredToken()` (`Authorization: Bearer <token>`). Без токена выводится предложение войти в систему.
   - Загрузка истории занятий (`fetchLessonsHistory`) также переведена на передачу токена с отображением подсказки при его отсутствии.
   - При статусе `failed` доступна кнопка «Повторить генерацию», отправляющая `POST` с телом `{"retry": true}`.

## 3. Внесённые изменения по файлам

1. `frontend_react/components/teacher/dds-lesson-report.tsx`:
   - Клиентский React-компонент `DDSLessonReport` с именованным экспортом.
   - Счетчик поколений `scopeGenRef`, синхронный замок `isPostingRef`, валидация `validateReportPayload`, сериализация опроса и отмена in-flight запросов.
2. `frontend_react/app/teacher/analytics/page.tsx`:
   - Подключение `DDSLessonReport` в раскрытую карточку завершённого урока ДДС.
   - Авторизация `fetchLessonsHistory` через `getStoredToken()`, подсказка входа при отсутствии токена.
3. `frontend_react/tests/27_teacher/dds-lesson-report.test.tsx`:
   - 12 модульных тестов: проверка авторизации, 404 без auto-POST, синхронной защиты от двойного POST, последовательного опроса, валидации payload (строго обязательный matching `lesson_id`, неизвестный статус, пустой completed text), монотонного счетчика поколений (A -> B -> A), немедленного сброса состояния, безопасного рендеринга текста, отмены без ложных ошибок, ручного обновления и перехода в ошибку при POST 409.
4. `docs/dds-report-teacher-ui.md`:
   - Настоящая документация архитектуры, протокола и проверок.

## 4. Ограничения и оставшаяся работа

- Независимую приёмку и запуск тестов/сборки выполнил техлид; фактические результаты приведены ниже.
- Исполнитель не выполнял изменений в БД, конфигурациях, docker-контейнерах и не производил commit/push/deploy.

## 5. Фактическая независимая приёмка 17.10.2026

- Antigravity выполнил все изменения продуктового кода, собственные тесты и
  исправления; техлид независимо проверил diff, подготовил acceptance-тесты,
  запускал команды и проверял браузер. RunCommand у Antigravity был запрещён;
  запрет не обходился, использовались разрешённые файловые инструменты.
- 24 независимых теста компонента, 12 тестов исполнителя и 6 регрессий входа и
  авторизации: **42 passed**. Production-сборка (`DOCKER_BUILD=false npm run build`)
  проходит. Сборка проекта настроена с `ignoreBuildErrors`; отдельно проверенный
  `tsc --noEmit` сохраняет 14 существующих ошибок, новых диагностик относительно
  базы нет. Три прежних падения `27_05_analytics.test.tsx` воспроизведены до и после
  изменений с теми же именами; они не объявлены исправленными.
- В изолированном браузерном стенде (loopback 3002, backend 8001, отдельная
  синтетическая SQLite) проверены вход преподавателя, загрузка реальной истории с
  Bearer, отсутствие блока у активного DDS и завершённого OPERATOR_112 занятия,
  создание реального Qwen-отчёта и восстановление после перезагрузки страницы.
- Для отдельного синтетического занятия временно остановлен только тестовый Qwen.
  Интерфейс показал `failed / llm_unavailable`; после восстановления runtime
  явный ручной повтор завершился `completed`, attempt=2. Перезагрузка страницы
  прочитала тот же сохранённый текст и attempt=2, без новой генерации.
- Независимые проверки выявили и помогли исправить отмену начального GET/POST,
  гонку A → B → A, принятие чужого/неполного ответа, ложное «отчёта нет» после
  ошибки POST и низкий контраст метаданных/предупреждения ИИ в существующей теме.

Это приёмка подключения интерфейса к А-04, а не полного учебного цикла. В
синтетическом тексте Qwen встречаются недоказанные характеристики ошибки и
причинные выводы об оценке. Общая методическая достоверность текста не принята.
Существующая история занятий также может показывать оценки, отличающиеся от
сохранённых исходных оценок отчёта; расчёт этих старых сводок не менялся в А-05.
Старая вкладка групповых ИИ-отчётов и её API не заменены новым блоком. Рабочее
демо на localhost:3000 не пересобиралось, облачный deployment не выполнялся.
