# Последовательное прохождение ДДС

Ветка `feat/dds-live-workflow`: серверная очередь подключена к прежнему АРМ,
выбору билетов, журналу и существующим сводкам. Общий quality gate пока красный:
старая независимая приёмка содержит ожидания прежнего деморежима и завершения.

## Запуск

- `POST /api/v1/lessons`: преподаватель передаёт `group_id`,
  `target_role: "DISPATCHER_DDS"`, `ticket_ids: [id1, id2, ...]` в порядке прохождения.
  Совместимый `ticket_id` означает один билет. Дубли, пустой набор и конфликт
  двух способов задания отклоняются. Чужая группа недоступна.
- `POST /api/v1/lessons/{lesson_id}/start`: проверяется весь набор до создания
  сессий; каждому активному участнику сохраняется отдельный снимок всего набора
  и создаётся только первая рабочая `IncidentCard`. Повтор старта ACTIVE занятия
  возвращает сохранённое состояние, даже если исходные билеты затем изменены.
- `GET /api/dds/training/tickets?category=...&complexity=1`: отдельный каталог
  для CADET, только ID/название/категория/подкатегория/сложность. Доступны active,
  published и прежние билеты без признака публикации; явные draft/inactive и
  удалённые/некорректные билеты исключены. Преподавательский каталог не открыт ученику.
- `POST /api/dds/training`: CADET передаёт `ticket_ids` и `request_id`.
  Повтор с тем же ключом и набором возвращает прежнюю сессию, включая завершённую;
  другой набор с тем же ключом даёт 409. Создание сериализовано по пользователю.
- Старые `/api/v1/sessions/demo` и `/api/v2/sessions/demo` используют тот же
  механизм очереди для одного сохранённого билета. При отсутствии билетов — 409,
  без создания фиксированной аварии. Существующая матрица ролей сохранена.

## Работа и завершение

`GET /api/dds/sessions/{session_id}` возвращает прежние поля текущей карточки и:

| Поле | Значение |
| --- | --- |
| `current_index`, `total_cards`, `completed_cards` | Индекс с нуля, размер набора, число закрытых карточек |
| `received_at` | Серверное время активации текущей карточки; не начало всего занятия |
| `card_submitted_at` | Время закрытия выбранной карточки |
| `can_complete`, `completion_blockers` | Возможность закрытия и причины блокировки по службам |
| `cards` | ID и состояния только уже полученных карточек; без будущих снимков |
| `readonly` | Для выбранной карточки доступен только просмотр |
| `stopped_at`, `stop_reason` | Досрочное завершение: `cadet` или `teacher` |

Внутренние `queue`, будущие фабулы и эталоны в ответ не включаются. Generic runtime
API не выдаёт `dynamic_state` сессии ДДС. `started_at` по-прежнему означает начало
сессии; АРМ использует `received_at` для текущей карточки.

`POST /api/dds/sessions/{session_id}/actions`: прежний payload плюс `card_id`.
Для многокарточного набора `card_id` обязателен; для одиночного старый payload
поддерживается. Новое действие для предыдущей карточки отклоняется. Точный повтор
сохранённого действия подтверждается без повторной записи, в том числе после перехода.
Автор (`actor_id`, сохранённый `actor_name`) и время задаются сервером.

`POST /api/dds/sessions/{session_id}/cards/{card_id}/complete` с `request_id`:

- Все службы должны иметь «Работы завершены» с сохранённым направлением либо
  мотивированный «Не принята»/«Отказ от выполнения работ»/сохранённый «Отказ».
- Направление требует непустых после trim «Кто принял» и «Суть».
  Последний этап «Работы завершены» без направления отклоняется заранее,
  пока реквизиты ещё можно сохранить.
- Закрытие, архивирование действий, результат `ungraded` без оценки и выдача
  следующей карточки — одна транзакция под блокировкой назначения.
- Повтор закрытия той же карточки не выдаёт ещё одну. Использование ключа
  закрытия другой карточки даёт 409. Возвращается актуальное состояние сессии.
- Последняя карточка завершает личную сессию. Самостоятельное назначение также
  завершается; групповое занятие остаётся под управлением преподавателя.

`POST /api/dds/sessions/{session_id}/finish` с `{}` теперь означает досрочное
завершение смены. Незакрытая карточка получает «Не завершено», `submitted_at`
остаётся null. Это **изменение поведения старого клиента**: обе UI-кнопки пока
вызывают `/finish`; на этапе 2 «отработана» нужно переключить на `/complete`.

`GET /api/dds/sessions/{session_id}/cards/{card_id}` читает текущую или ранее
полученную собственную карточку; архив readonly. Преподаватель может читать
работы своего занятия, но не отправлять действия за ученика. Чужие ID недоступны.

## Хранение и совместимость

Используются прежние таблицы и `Assignment.card_pool_ids`; DDL/миграций нет.
`ExamSession.dynamic_state.dds.version = 2` хранит серверную очередь снимков,
текущий индекс и архив закрытых карточек. Прежние ключи `incoming_card`, `card_id`,
`actions` проецируют текущую карточку; `submitted_at` относится ко всему прохождению.
`IncidentCard.filled_data` остаётся неизменяемым снимком, действия — отдельно.

Старые состояния без версии читаются как одна карточка без переписывания истории.
Уже завершённые записи не меняются. Раннее завершение активной старой сессии
также не считается успешной сдачей.

## Интерфейс

Преподаватель выбирает несколько билетов с сохранением порядка и фильтрами категории
и сложности в прежней форме занятия. В лобби ученик выбирает собственный набор из
безопасного каталога. Самостоятельный запуск открывает существующий список происшествий;
«Взять карточку в обработку» открывает прежний АРМ. `/dds` без занятия ведёт в список.

«Отработана» закрывает текущую карточку и получает следующую, «Завершить смену»
досрочно останавливает прохождение. Кнопки используют разные операции сервера.
Черновики и учебный звонок сбрасываются при переходе, URL обновляется;
неопределённый результат сохранения повторяется с прежними card_id/request_id.
При серверном отказе можно исправить данные. Журнал включает ранее полученные
карточки; закрытые доступны только для просмотра. История ученика, прогресс
преподавателя и данные отчёта учитывают весь набор, без вымышленных оценок.

## Проверки

```bash
env -u DATABASE_URL -u SECRET_KEY python -m pytest tests/test_dds_queue.py -q
python scripts/check_dds_queue_postgres.py
env -u DATABASE_URL -u SECRET_KEY bash scripts/verify_build.sh backend-core
```

Pytest выделяет приватную SQLite до импорта backend. PostgreSQL-проверка сама
создаёт контейнер PostgreSQL 15 с отдельным случайным локальным портом и удаляет
только этот контейнер/его том после проверки; чужие подключения не используются.
Она выполняет те же API-сценарии, включая конкурентные запросы, через ASGITransport.
Дополнительно выполнены браузерные проверки на отдельной синтетической SQLite,
TypeScript и production build. Реальный ИИ, полноценный телефон и облачный выпуск
не входят в эту проверку.

Старые независимые тесты не переписаны. Ожидания успешного `/finish` без полного
цикла, конечного статуса без направления, создания занятия без билета и генерации
фиксированного билета при пустой базе конфликтуют с новым контрактом; общий
quality gate остаётся красным до актуализации этой приёмки по новому контракту.
