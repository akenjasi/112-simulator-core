## Исправить в первую очередь

### 1. Редактирование эталона меняет исходные факты происшествия

`backend/api/router_tickets.py:1235`: даже PATCH только с `dds_etalon` запускает `build_incoming_card` из старого `ground_truth`. Если актуальные факты существуют только в `content.incoming_card`, они теряются.

Воспроизведение: исходная карточка содержит адрес «Точный адрес», пострадавшие «да», блокировка «да». Сохранить только новое ожидаемое решение. Признак пострадавших становится «нет»; входящая карточка пересоздаётся из другого набора данных.

Нужно: изменение критериев не меняет исходную карточку. При изменении самих фактов использовать однозначный источник и сохранять остальные сведения. Не маскировать проблему изменением тестового ожидания.

Тест: `test_editing_etalon_alone_does_not_rebuild_or_erase_original_card_facts`.

### 2. Смешиваются разные попытки в одной сессии

`backend/api/router_analytics.py:633, 697`: `dds.actions` и входящая карточка сессии используются для любой открытой записи, даже если `dds.card_id` указывает на другую карточку и исторический снимок не соответствует её билету.

Нужно: проверить связь журнала и контекста с конкретной попыткой/карточкой. Для другой работы без собственного журнала показывать отсутствие данных, а не действия соседней работы.

Тест: `test_other_attempt_does_not_inherit_current_session_card_and_actions`.

### 3. События без подтверждённого автора приписываются курсанту

`backend/api/router_analytics.py:641`: отсутствие `actor_id` пропускается как допустимое авторство. Автоматический статус с комментарием также попадает в действия курсанта.

Нужно: собственные действия подтверждаются автором; неизвестное авторство нельзя выдавать за установленное. Автоматическое событие с пояснением системы не становится самостоятельным действием обучающегося. Полезные неподтверждённые исторические события можно показать отдельно с честной подписью.

Тест: `test_unknown_author_and_system_comments_are_not_cadet_actions` (2 случая). Положительный тест исключения известного другого автора и сохранения собственного комментария уже проходит.

### 4. Служба задания и результат берутся от разных служб

`backend/api/router_analytics.py:719, 747, 761, 783`: служба задания — первый получатель уведомления, решение — первое подходящее действие, итог — последний статус любого получателя.

Воспроизведение: эталон задан для 104, список получателей начинается с 101. Курсант принял за 101, отказался за 104 и завершил за 101. UI сообщает службу задания 101 и результат 101 рядом с требованиями 104.

Нужно: использовать явно заданный профиль и сопоставлять решение/время/результат той же службы. Если действия охватывают несколько служб, показывать принадлежность; не смешивать их в один итог. Без явно заданного профиля не назначать его по порядку уведомлений.

Тесты: `test_assigned_service_comes_from_task_not_first_notification_recipient`, `test_no_task_service_is_invented_from_notification_order`, `test_decision_and_final_status_refer_to_task_service`.

### 5. Старый мусор вернулся через fallback

`backend/api/router_analytics.py:829` возвращает исходную карточку как `student_answer`, если действий нет. `frontend_react/components/teacher/split-screen.tsx:232` продолжает объединять произвольные ключи и рисовать их в колонках эталона и ввода.

На реальном формате старых данных снова появляются `fio`, `caller_status`, `caller`, `aon`, `ambulanceRefusal`, а значение `visclass: bg-red-500` проходит через фильтр, который исключает только `visClass`. Исходный заявитель показан в колонке «Ввод курсанта» даже при сообщении, что действий нет.

Нужно: для DDS использовать предметное представление с разрешёнными полями. Сохранённые входящие сведения показывать в контексте. Не сохранять универсальный перебор ключей «для существующих тестов». Регрессию старых форматов решать адаптером данных; технические ключи не выводить как подписи.

Тест backend: `test_no_actions_does_not_return_initial_card_as_student_authored_answer`.
Тесты UI: `does not present incoming legacy card fields as cadet authored answer`, `does not leave raw legacy keys and CSS values in the DDS etalon`.

## Прочие подтверждённые проблемы

### 6. Время подтверждения подменено временем от старта сессии

`router_analytics.py:637, 763`: `start_time` без доказательства трактуется как время направления карточки. Для старой сессии с подтверждением на 18-й секунде после старта выводится «18 секунд с момента направления», хотя направление не зафиксировано. Кроме того, явно сохранённое `confirmation_time_limit_seconds: null` заменяется на 30 и на backend, и на frontend.

Нужно: хранить/использовать подтверждённое событие направления для конкретной карточки/службы. Если в новом пути старт одновременно является направлением, фиксировать это явно для новых попыток; не распространять допущение на старые. Время от старта можно отдельно показывать именно под этой подписью. Не подменять незаданный норматив значением по умолчанию при чтении истории.

Тесты: `test_session_start_is_not_unconditionally_claimed_as_delivery_time`, `test_explicitly_unset_timing_requirement_is_not_replaced_by_thirty`; UI `does not replace an unspecified historical time requirement with thirty seconds`.

### 7. Завершённая работа без оценки показана как «Не зачтено»

`split-screen.tsx:346`: любое состояние, кроме `passed`, попадает в отрицательную ветку. `status=completed, score=null` получает «Не зачтено».

Нужно: отдельно отображать отсутствие оценки и состояния выполнения. Балл без сохранённого решения о зачёте также не означает автоматически провал.

UI-тест: `does not claim an ungraded completed work has failed`.

### 8. Некорректная обработка и редактирование эталона

- `DDSEtalon` принимает отрицательный/нулевой срок и `true` как 1 секунду. Нужно положительное целое без преобразования bool; дробное значение 1.5 уже отклоняется.
- `router_analytics.py:684`: некорректный исторический эталон получает `has_dds_etalon=true`, хотя проверка модели провалилась и объект отсутствует.
- Эталон только со службой и явным сроком 45 секунд отбрасывается; отображается 30. Не терять реально заданные частичные требования.
- PATCH `dds_etalon: null` не удаляет эталон: отсутствие поля и явное удаление обрабатываются одинаково. Учитывать наличие ключа и очищать обе хранящиеся копии без восстановления через fallback.

Тесты: `test_invalid_confirmation_limit_is_rejected_by_ticket_api`, `test_invalid_historical_etalon_is_not_reported_as_present`, `test_service_and_timing_only_etalon_is_not_discarded`, `test_api_allows_explicit_removal_of_ticket_etalon`.

### 9. `[object Object]` остался в ошибках

`split-screen.tsx:213`: объект вида `error_details.comment = {message: 'Причина отказа не указана', severity: 'error'}` превращается в `String(val)`. На экране `[object Object]`, полезный текст потерян.

Нужно: нормализовать структурированные ошибки, сохранять сообщение и важность; неизвестную структуру не печатать техническим представлением.

UI-тест: `renders structured historical errors without object Object or losing the explanation`.

### 10. Полный разбор не показывает отдельно оценки ИИ и преподавателя

Поля `automatic_score` и `expert_score` объявлены, но в `SplitScreen` не отображаются. Видна только общая надпись «Балл». В диалоге оценки разделение есть, в полном разборе теряется.

Нужно: показать обе сохранённые оценки и честное отсутствие каждой. Не генерировать ИИ-оценку и не смешивать её с экспертной.

UI-тест: `shows the separately saved AI and teacher scores in the full grading view`.
