## Исправить в первую очередь

### 1. У одной попытки расходятся оценки при разных record_id

`backend/api/router_analytics.py`, `override_record_grade` (~915) и разрешение связей в `get_record_detail`.

При связанном TicketResult с экспертным баллом 91 и EvaluationResult с исходным баллом 84 POST по evaluation_id с новым баллом 73.5 отвечает 200, но изменяет только EvaluationResult. При чтении используется приоритет TicketResult и итог остаётся 91. В аудит попадает прежний 84 вместо действующего 91.

Нужно: сначала однозначно разрешать попытку по любому поддерживаемому ID; читать действующий итог и сохранять согласованную экспертную оценку одной попытки. Для неоднозначных связей нельзя угадывать чужой результат. Ответ POST, повторный GET по всем ID этой же попытки, история и аудит должны согласовываться.

Тест: `test_grading_by_evaluation_alias_updates_the_same_attempt_as_result_alias`.

### 2. Несданная работа становится доступной для оценки после закрытия урока

Backend: `override_record_grade` (~946–965). UI: история уроков, условие `isTicketActive` (~2048).

Если личная DDS-сессия имеет COMPLETED, но submitted_at отсутствует, backend принимает первую оценку. История показывает кнопку для работы со статусом INCOMPLETE / incomplete: проверяется только IN_PROGRESS.

Нужно: проверять факт отправки DDS-работы независимо от завершения урока. Для несданного ответа нет кнопки, API возвращает 409 без изменения результата и аудита. Отправленный ответ с отсутствующей оценкой остаётся доступным для первой оценки.

Тесты: `test_completed_but_unsubmitted_dds_attempt_is_not_eligible_for_first_grade`, UI `does not offer grading for a closed DDS lesson whose work was not submitted`.

### 3. Старая экспертная оценка ошибочно выдаётся за исходную оценку ИИ

Backend: `override_record_grade` (~967–973).

При исторической EvaluationResult с is_appealed / expert_modified_at и без сохранённого automatic_score код копирует прежний final_score в automatic_score. Например, прежний экспертный 84 становится «Оценкой ИИ: 84», хотя оригинальная оценка ИИ неизвестна.

Нужно: сохранять известную исходную автоматическую оценку при первой экспертной правке. Если запись уже экспертная, а исходная автоматическая потеряна, automatic_score остаётся null. Нельзя восстанавливать её из прежнего экспертного балла.

Тест: `test_legacy_expert_grade_is_not_relabelled_as_original_ai_score`.

### 4. Введённые балл и комментарий перезаписывает поздний GET

Frontend: `components/teacher/grade-dialog.tsx`, effect загрузки (~49–101).

Открыть форму, до завершения GET ввести 73.5 и новый комментарий, затем вернуть старые данные 84 / старый комментарий. Форма заменяет пользовательский ввод старыми значениями. Можно сохранить другой балл, чем только что ввёл преподаватель.

Нужно: либо корректно блокировать редактирование на загрузке, либо заполнять с сервера только ещё не изменённые пользователем поля. Не терять введённые значения, не применять данные старой карточки к новой.

Тест UI: `does not overwrite an entered grade or comment when the initial GET finishes late`.

### 5. При оценивании через TicketResult не возвращается экспертный балл

Backend: `override_record_grade` и `get_record_detail` (~590–615).

Если есть связанная оценка ИИ и оценка меняется по result_id, итоговый score обновляется, automatic_score = 84 остаётся, но expert_score возвращается null: GET берёт метаданные из неизменённой EvaluationResult и игнорирует экспертную правку TicketResult. Могут отсутствовать и автор/время экспертной правки.

Нужно: раздельные automatic_score/expert_score и автор/время должны соответствовать реально применённой итоговой экспертной оценке, независимо от использованного ID. Не решать это потерей исходного ИИ-балла или созданием дублей попыток.

Тест: `test_ticket_result_override_exposes_expert_score_and_author_when_ai_exists`.

### 6. Старый разбор после успешной числовой правки показывает прежний балл

Frontend: `app/teacher/analytics/page.tsx`, `handleAppeal` (~674–773), и `components/teacher/split-screen.tsx`.

Из разбора изменить 84 на 73.5. POST успешно сохраняет 73.5, но возвращает new_score. Родитель объединяет ответ с выбранной записью без обновления score / повторного чтения деталей. На экране остаётся «Балл: 84%». Локальный статус при этом меняется по старому селектору passed/failed.

Нужно: использовать согласованный числовой механизм и повторно читать действительную запись после сохранения; обновлять историю и загруженные сводки. Не подставлять статус и балл самостоятельно. Новая форма из истории тоже сейчас обновляет историю и сессию, но не загруженные графические агрегаты.

Тест UI: `refreshes the displayed score after a numeric revision in the existing split-screen`.

## Прочие незавершённые пункты ТЗ

- В новом диалоге показываются имя, название и баллы, но нет ответа курсанта, эталона или перехода к разбору выбранной работы. Требование контекста оценивания осталось невыполненным.
- Старый сплит-скрин получил дополнительный опциональный числовой input, но сохранил отдельную форму с прежним статусным сценарием, а не общий компонент числовой оценки. Необходимо убрать расхождения в валидации и обновлении результата между входами в оценивание.
- В истории остаётся fallback `record_id || card_id || ticket_id`. ID сценария не заменяет ID результата. При отсутствии однозначного ID нужна понятная недоступность действия / ошибка загрузки данных, а не попытка записи по ID билета.
