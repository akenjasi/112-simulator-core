# Локальный inference отчётов

Отчёты работают с локальной Qwen3.5-4B-Q4_K_M.gguf через llama.cpp `/v1/chat/completions`. Штатная конфигурация рассчитана только на CPU: `--n-gpu-layers 0`, четыре потока, один слот, контекст 8192. Интернет нужен для подготовки весов и образов; во время анализа внешних запросов нет. Контракты и права описаны в [отчётах ДДС](../product/reports.md).

## Подготовка и запуск

Вес: `models/llm/Qwen3.5-4B-Q4_K_M.gguf`, 2 740 937 888 байт. Источник — [Unsloth Qwen3.5-4B-GGUF](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF), закреплённая ревизия `e87f176479d0855a907a41277aca2f8ee7a09523`. SHA-256: `00fe7986ff5f6b463e62455821146049db6f9313603938a70800d1fb69ef11a4`. Offline-упаковщик скачивает и проверяет именно этот файл; startup приложения веса не скачивает.

Создайте приватный `.env.llm` в корне проекта из `.env.llm.example` и задайте существующий абсолютный `DDS_LLM_MODEL_PATH`. Его наличие включает CPU inference в обычные `make up`, `make up-prod`, `make down` и `make logs`. `WITH_LLM=0` явно отключает это подключение; без подготовленного файла базовый запуск не требует модели. Для backend на хосте адрес — `http://127.0.0.1:8081/v1`; внутри Compose bridge задаёт `http://llm:8080/v1`. Алиас `DDS_LLM_MODEL` должен совпадать у backend и runtime; в примере это `dds-qwen`. Сохранённое поле model_used содержит этот алиас.

```bash
make up
# Либо конфигурация вне проекта:
make up LLM_ENV_FILE=/absolute/private/.env.llm
```

Для logs/down передавайте те же `PROJECT` и внешний `LLM_ENV_FILE`, если они переопределены. `.env.llm` в корне проекта подхватывается автоматически. Отдельный runtime без приложения запускается через `make llm-up`. Runtime монтирует веса read-only и не создаёт отсутствующий файл. Не добавляйте веса и реальные env-файлы в Git. CPU image закреплён digest; сборка b11723 поддерживает Qwen3.5 и используемые параметры кэша. Существующий отдельный GPU Compose остаётся опциональной конфигурацией для других установок; для этой модели он не нужен.

При запуске с inference backend ожидает healthy сервиса `llm`, чтобы не принимать генерацию во время загрузки весов. Успешный `/health` backend не доказывает дальнейшую доступность модели: проверьте также `/health` inference. При `llm_unavailable` сначала убедитесь, что сервис `llm` запущен в той же сети и backend использует `http://llm:8080/v1`. Удаление контейнеров/томов не удаляет приватный `.env.llm` и веса на хосте; следующий `make up` снова поднимет модель. Изменения файлов конфигурации не меняют запущенные процессы до пересоздания сервиса. Неудавшийся отчёт повторяется кнопкой «Повторить генерацию», персональный — «Повторить анализ ИИ».

## Кэш системных промптов

Инструкции находятся в `backend/prompts/reports`: общий контракт, отдельные задачи `dispatch` и `report`, отдельные аудитории `teacher` и `student`. Эти части образуют четыре постоянных системных промпта. Тексты карточки, эталона, доклада и ответа находятся только в пользовательском сообщении. Служебные идентификаторы, ссылки и время не отправляются модели: приложение добавляет их к проверенному разбору самостоятельно, сокращая обработку входа на CPU. Python сохраняет загруженные инструкции, а llama.cpp повторно использует обработанный префикс через `cache_prompt=true`, один слот и контекстные checkpoints для гибридной архитектуры Qwen3.5. Сравнения одного типа обрабатываются последовательно, без смены системного промпта.

CPU Compose задаёт `--cache-prompt`, `--cache-ram 512`, `--ctx-checkpoints 16`, `--checkpoint-min-step 256`. Это кэш вычисленного состояния, а не только файла промпта. Первое обращение к новому префиксу требует обработки; последующие переиспользуют доступные checkpoints. Для переключения типов задач backend дополнительно сохраняет и восстанавливает состояние слота через `/slots/0?action=save/restore`. Ключ файла зависит от модели и точного текста системного промпта, а не от ответа курсанта. CPU Compose монтирует отдельный Docker volume `llm_prompt_cache` в `/cache`. Это сохраняет кэш каждого промпта без четырёх параллельных контекстов в RAM. При отсутствии файла или несовместимом состоянии запрос обрабатывается заново; при первом обращении `/apply-template` выделяет системный префикс, `/completion` с `n_predict=0` однократно обрабатывает его, после чего сохраняется только это состояние. Пользовательские записи в файл системного кэша не включаются. Ошибка кэша не подменяет содержательный разбор шаблоном. Абсолютного обещания «системный промпт никогда не считается заново» нет. Сведения о `cached_tokens` видны в runtime timings и диагностическом журнале backend, без содержимого записей.

`DDS_LLM_SLEEP_IDLE_SECONDS=-1` по умолчанию сохраняет веса и кэш в памяти между запросами. Для освобождения памяти можно задать, например, `600`; после сна RAM-кэш утрачен, сохранённое состояние восстанавливается с диска при следующем запросе. RAM-кэш ограничен `DDS_LLM_CACHE_RAM_MB=512`. Снимки системного префикса находятся в отдельном volume, который не публикуется в API. Ответы курсантов в эти файлы не сохраняются. `DDS_LLM_SLOT_CACHE=false` отключает сохранение/восстановление. При замене весов под прежним алиасом старый volume кэша нужно очистить; изменение текста инструкции автоматически меняет ключ. Готовые отчёты сохраняются в БД; их чтение модель не вызывает. Изменение текстовых файлов промптов требует перезапуска backend.

## Нагрузка

Один запрос к модели выполняется одновременно, включая деморежим. Рассуждение отключено; ответ ограничен 1200 токенами и строгой JSON-схемой. Анализ разбит на отдельные пары исходного доклада и сохранённой записи, без выборки только первых участников. Превышение лимита отдельной пары или незавершённый ответ не приводит к публикации частичного отчёта. Цитаты проверяются по исходным текстам. Завершённый, но непроверяемый ответ исключается только для соответствующей записи с явным ограничением в итоговом отчёте; если ни один ответ вызванной модели не прошёл проверку, задача завершается ошибкой. Смысловые выводы всё равно остаются методическим заключением модели. Реальное занятие с восемью сравнениями и отдельными персональным и общим отчётами требует шестнадцати последовательных запросов и на CPU может занимать десятки минут; короткие синтетические примеры ниже не измеряют время всего занятия.

В `queued` отчёты ждут отсутствия активных занятий/сессий, CPU ниже 40% непрерывно 30 секунд и достаточного запаса памяти. Забытые ACTIVE-сессии блокируют всю очередь. Резерв RAM — 2048 MiB; бюджет холодной загрузки 4B с кэшем — 4608 MiB (`DDS_REPORT_MODEL_BUDGET_MB`). Это предварительный бюджет, его уточняют на целевом сервере. При доступной памяти менее 1 GiB worker прерывает анализ. Для загруженной модели применяется свободный резерв, а не повторный бюджет весов.

Перед учебной работой поток отменяется и `/slots` подтверждает остановку; `DDS_REPORT_CANCEL_TIMEOUT_SECONDS=30`. CPU batch/ubatch — 256/128: отмена обрабатывается между блоками. Частичный текст не публикуется. `DDS_LLM_TIMEOUT_SECONDS=900` ограничивает каждое сравнение. Отчёт из нескольких записей требует нескольких последовательных сравнений; кэш ускоряет чтение инструкции, но не генерацию новых слов.

`DDS_REPORT_MODE=demo` запускает отчёты сразу по завершении всего занятия, без проверки нагрузки и окна простоя. Он подходит выделенному демонстрационному стенду; новое занятие не отменяет эти демозапросы. `queued` сохраняет обычный планировщик и семидневные отчёты. Баллы преподавателя для содержательного разбора не требуются.

## Проверка настоящей модели

Синтетическая проверка содержания не читает рабочую БД. Она проверяет обнаружение неверной бригады, допустимый пересказ с номером цифрой, пропуск результата работ, границы анализа первой телефонограммы и восстановление кэша после переключения задач; печатает время и сведения о кэше:

```bash
python -m backend.scripts.check_report_content --base-url http://127.0.0.1:18081/v1 --output data/reports/qwen-cpu-validation.json
python -m backend.scripts.check_report_runtime --base-url http://127.0.0.1:18081/v1
```

Для отдельного runtime с включённым idle sleep добавьте ко второй команде `--expect-sleep`; `--container NAME` позволяет проверить падение RSS после сна. Проверка использует отдельный экземпляр и не должна отменять чужие запросы. Все измерения скорости относятся к проверенному CPU, не являются гарантией для другого сервера. ASR/TTS и операторские модели остаются отдельными потребителями памяти.

Проверка 20.10.2026 на закреплённом CPU image b11723: шесть синтетических случаев прошли, включая другие ФИО/бригады, пропуск деблокирования и передачи медикам, допустимый пересказ и возврат к прежней задаче. На четырёх потоках тёплые сравнения заняли примерно 28–52 секунды; после смены типа задачи восстановлены 1132 токена префикса. Это измерение отдельных записей, не всего занятия; первый запрос нового промпта дополнительно обрабатывает системную инструкцию. Сырые результаты локальной проверки находятся в `data/reports/qwen-cpu-validation.json`; команда выше воспроизводит проверку без рабочей БД.

После применения конфигурации контрольный запрос из запущенного backend к `http://llm:8080/v1` с алиасом `qwen3.5-4b-q4_k_m` также прошёл: выявлен потерянный результат работ, приведены исходные цитаты и исправление. Первый запрос с подготовкой нового системного кэша занял 88.7 секунды. Backend и inference healthy; фактический запуск использует ноль GPU-слоёв и не подключает GPU-устройства.
