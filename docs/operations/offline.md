# Поставка без интернета и GPU

Скрипты находятся в `docker/offline/`: `package.sh` собирает поставку,
`deploy.sh` разворачивает её на сервере. Это прежние `package_offline.sh` и
`deploy_offline.sh`, перенесённые из корня и адаптированные к новой структуре:
интерфейс берётся из `frontend/`, Dockerfile — из `docker/images/`, зависимости
backend — из `backend/requirements/`, ресурсы — из `assets/`.

Упаковщик **не запускает и не обновляет
рабочий стенд**: собирает образы на машине с интернетом и создаёт один архив для
Linux/amd64. Другие архитектуры не заявляются. Распознавание речи в этой поставке
отключено: ASR-модель не нужна и в архив не включается.

## Упаковка

Нужны Docker с Compose, Git, Bash, Python 3.11+, curl и обычные Linux-утилиты.
Перед сборкой общий загрузчик `tools/provision_models.py` проверяет и при отсутствии
скачивает закреплённые модели из `tools/models.json`:

- Qwen3.5-4B Q4_K_M, 2 740 937 888 байт, в `models/llm/` —
  [Unsloth, ревизия e87f176](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF/tree/e87f176479d0855a907a41277aca2f8ee7a09523).
- Qwen TTS talker 0.6B Q4_K_M и tokenizer 12hz Q4_K_M, вместе 883 879 808 байт,
  в `data/tts_models/` —
  [Serveurperso, ревизия b7ee2e8](https://huggingface.co/Serveurperso/Qwen3-TTS-GGUF/tree/b7ee2e8c7459c3bea99da23e3d178125a7d1713c).

Размеры и SHA-256 проверяются до сборки. Готовые исправные файлы не скачиваются
повторно. После обрыва загрузка продолжается из `.part`, включая до пяти повторов
после сетевых ошибок; параллельные процессы используют файловую блокировку.
Повреждённый готовый файл сохраняется: исправьте его явно и повторите команду.
Веса, `.part` и `.lock` исключены из Git. `TTS_MODELS_DIR` задаёт другой каталог
TTS; относительные пути считаются от корня проекта.
Классификатор и native-библиотеки берутся из подготовленного локального комплекта;
отсутствие обязательного ресурса останавливает упаковку до загрузки и сборки.

```bash
# Скачать LLM и TTS (если их ещё нет), собрать образы и упаковать всё:
make package-offline

./docker/offline/package.sh \
  --version release-1 \
  --work-dir /srv/tmp \
  --output /srv/export/simulator112.tar.gz
```

`--llm-model /srv/models/custom.gguf` позволяет использовать свой готовый
однофайловый GGUF без скачивания. Аналогично работает `DDS_LLM_MODEL_PATH`.
При отсутствии явно указанного файла скрипт останавливается, не подменяя модель.
`--no-download` запрещает загрузку весов. `--check` ничего не скачивает и не
собирает: проверяет наличие весов и готовность Docker. Если обязательной модели ещё нет,
эта проверка сообщит об отсутствующем файле.

Нужно место под образы, копии весов и итоговый сжатый архив одновременно.
Временная сборка по умолчанию размещается в `.work` рядом с итоговым архивом
(для стандартного запуска — `data/packages/offline/.work`). `/tmp` и `TMPDIR` для неё
не используются: на многих системах это небольшой раздел в оперативной памяти
с отдельной квотой, независимо от свободного места на диске. `--work-dir` позволяет
явно выбрать другой диск. При выходе временный каталог сборки удаляется;
скачанный оригинал модели остаётся в `models/`.
Сборка использует текущие отслеживаемые Git файлы, включая их незакоммиченные
правки. Новый исходник, ещё не добавленный в Git, в контекст не попадёт.
Локальные секреты и рабочие данные туда не копируются. Веса классификатора могут
быть локальными: необходимые известные файлы копируются явно.

В поставку входят четыре образа, веса, CPU Compose без секции `build` и GPU,
контрольные суммы, установка, запуск/остановка, проверка, backup/restore и README.
Backend и frontend собираются, PostgreSQL и официальный CPU llama.cpp скачиваются
на машине упаковки, затем все четыре образа сохраняются `docker image save`.
Перед сохранением образов упаковщик выполняет настоящий синтез в backend-контейнере без сети и рабочих данных; ошибка останавливает выпуск архива. Для воспроизводимого переноса сохраняются именно эти образы и их ID, а не только
ссылки на обновляемые внешние теги.

## Перенос уже наполненной базы

Добавьте `--with-data --source-project 112-simulator-core`. Это экспортирует
PostgreSQL и `/app/data` из существующих контейнеров, не останавливая их. Учебную
работу на время экспорта следует прекратить, чтобы файлы соответствовали снимку
БД. Архив будет содержать реальные учётные записи и материалы; храните его как
резервную копию. Текущие `.env` и TLS-ключи в него не добавляются.

## Установка на закрытом сервере

Нужен установленный Docker Engine с Compose. Python, Node, PostgreSQL, GPU,
CUDA и NVIDIA Container Toolkit на хосте не нужны.

Скопируйте на сервер архив, соседний файл `.sha256` и скрипт
`docker/offline/deploy.sh`, сохранив его как `deploy.sh`. Репозиторий целиком
переносить не нужно. На сервере:

```bash
bash deploy.sh /путь/simulator112.tar.gz \
  --directory "$HOME/simulator112"

# Если архив собран с --with-data и требуется перенести базу и материалы:
bash deploy.sh /путь/simulator112.tar.gz \
  --directory "$HOME/simulator112" --restore
```

Это альтернативные варианты установки; выберите один. Скрипт проверяет архив,
отклоняет небезопасные пути и ссылки, проверяет свободное место, распаковывает
рядом с выбранным каталогом (не в `/tmp`) и вызывает комплектный `install.sh`.
Тот загружает образы, создаёт пароли, запускает сервисы и проверяет локальную LLM.
Ничего не скачивается. Дополнительное место под загруженные образы требуется
также в хранилище самого Docker. Пользователь должен иметь доступ к Docker.
Существующий каталог установки не перезаписывается. После ошибки установщика
файлы остаются для диагностики; повторите `install.sh` из этого каталога.
Для отдельного Compose-проекта есть `--project NAME`; при последующих операциях
используйте тот же `export SIMULATOR_PROJECT=NAME`, который выведет скрипт.

Если архив уже распакован, отдельный скрипт не нужен:

```bash
tar -xzf simulator112.tar.gz
cd simulator112-offline
./install.sh             # чистая установка
# либо ./install.sh --restore — для поставки с экспортом БД и файлов
```

Установщик создаёт `.env` с новыми секретами и паролем первого администратора.
Для восстановленных аккаунтов сохраняются прежние пароли. Данные живут в томах
Docker и переживают замену контейнеров. Образы загружаются из архива; скачивания и
сборка на сервере запрещены. Backend доступен через Nginx; БД и LLM наружу не
публикуются. Для HTTPS из локальной сети подготовьте сертификат нужного адреса,
доверенный браузерами курсантов.

`verify.sh` ждёт готовности backend, интерфейса и LLM, затем выполняет
синтетическую генерацию без реальных занятий. Наличие собранного архива само по
себе не подтверждает скорость и работоспособность выбранной модели на сервере.

**Синтез речи:** веса TTS обязательно находятся в `models/tts/` архива и монтируются
read-only; бинарник `qwen-tts`, библиотеки и образцы голосов находятся в backend image.
TTS включён по умолчанию (`TTS_ENABLED=true`), установочная проверка генерирует
настоящий WAV: PCM16, моно, 8 кГц. Существующий аудиокэш не требуется; `--with-data`
может дополнительно перенести его. `TTS_ENABLED=false` явно отключает синтез.
Legacy TTS с отдельным HTTP-сервисом не входит в этот комплект. ASR выключен.

`bash docker/scripts/pack_release.sh` вызывает этот же упаковщик. `RELEASE_DIR`
задаёт каталог назначения (по умолчанию `data/packages/release`); результат —
версионированный `.tar.gz` и `.sha256`. Прежний каталог с тремя images заменён
полным комплектом из четырёх images и моделей. Аргументы, включая `--output`,
`--version`, `--check`, `--no-download` и `--llm-model`, передаются упаковщику.

Генератор текстовых реплик подключается к общему CPU LLM через новые настройки
`FACTOIDS_LLM_BASE_URL/MODEL/TIMEOUT_SECONDS`; значения по умолчанию в разработке
сохраняют прежний адрес Ollama.

## Проверка самого упаковщика

```bash
python3 -m unittest discover -s docker/offline/tests -p 'test_offline_*.py' -v
```

Контрактные проверки используют записывающие имитации Docker и загрузчика: комплектность архива и
контрольных сумм, отсутствие секретов, перенос данных только по флагу, корректную
архитектуру, отказ при ошибке сборки/отсутствии моделей/повреждении весов, повторную
установку без смены паролей и отказ восстановления поверх существующей БД.
Также проверяются загрузка и повторное использование весов, продолжение после
обрыва, отказ при повреждении, исключение весов из Git и запрет загрузки в `--check`.
Это не тест реального inference. Проверки упаковщика добавлены в Quality Gate.
Дополнительные 9 проверок серверного скрипта покрывают распаковку и запуск
установщика, восстановление, повреждённый архив, сохранение существующих файлов,
небезопасные пути/ссылки, нехватку места и сохранение диагностики после ошибки.
Отдельно прошли 5 адресных pytest-проверок маршрутизации LLM, прежнего генератора
и сохранности frontend ДДС; проверены Compose и входящий HTTP-доступ через две
сети на временном контейнере.

Полная сборка комплекта с весами и запуск реальной модели на момент разработки
не выполнялись: многогигабайтная загрузка в ходе разработки не запускалась.
В дополнительном старом `backend/tests/test_api.py` остаются два ожидания 200 вместо 403;
те же падения воспроизведены на исходном main `22def95`, права доступа не менялись.
