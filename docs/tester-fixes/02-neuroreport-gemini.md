# FIX-02 — нейроотчёт завершённого занятия ДДС

Сложность: высокая. Это отдельное задание Gemini. Продуктовый код в ходе диагностики не изменялся. Нужны исправление данных отчёта и проверка подключения локальной модели; интерфейс самого занятия ДДС менять запрещено.

## Подтверждённый диагноз (18.10.2026)

1. **Локальный backend не подключён к LLM.** Read-only проверка работающего `simulator_backend` показала: `DDS_LLM_BASE_URL_CONFIGURED=False`, `DDS_LLM_MODEL_CONFIGURED=False`, адрес по умолчанию является loopback контейнера, TCP-порт недоступен (`DDS_LLM_TCP_REACHABLE=False`). Среди запущенных контейнеров только backend/frontend/postgres. В `dds_report_llm.py` default — `http://127.0.0.1:8081/v1`; в контейнере это сам backend, а не хост. `docker-compose.llm.yml` запускается отдельно и публикует LLM лишь на loopback хоста. Значит для дошедшего до HTTP запроса отчёта текущий runtime завершится ошибкой доступности. Генерация и рабочие report jobs при диагностике не запускались; содержимое настроек, рабочие снимки и персональные данные не читались.
2. **Теряется фактический протокол ДДС.** `collect_lesson_report_data()` читает карточки/оценки/результаты билетов, но не переносит `dynamic_state.dds.actions` и `completed_cards[].actions` в снимок. Модель `DDSReportSessionItem` тоже не содержит действий: произвольно добавленные поля Pydantic отбросит. В assigned_services остаётся только безопасная история статусов, без сохранённых объяснений действий. Особенно теряется контекст карточки, остановленной преподавателем до завершения.
3. **Проверка достаточности данных использует число строк вместо фактов.** `generate_dds_lesson_report()` требует `evaluation_count > 0 OR ticket_result_count > 0`. Поэтому занятие с сохранёнными действиями без строк результатов отклоняется (`insufficient_data`). При этом `complete_card()` создаёт `TicketResult(status="ungraded", score_total=None, is_passed=False, errors_count=0)`: даже пустая такая строка проходит guard. `False` и `0` здесь значения по умолчанию, не свидетельства провала или безошибочной работы. Нельзя снимать блокировку с любого пустого занятия или фабриковать оценки ради отчёта.
4. **Обработка jobs/UI существует.** Worker включён в lifespan, сохраняет snapshot на создание/retry, использует attempt guard; teacher UI опрашивает каждые 2 секунды и показывает failed. Это не «кнопка вообще никуда не подключена». Сохранённые failed jobs автоматически не перезапускаются: нужен явный retry с новым снимком. Временная ошибка polling останавливает автоматическое ожидание и требует «Обновить»; учесть это при диагностике, не заменять весь механизм.

## Задание

- Обеспечить фактический отчёт по сохранённым действиям текущей и архивных карточек выбранного завершённого DDS занятия. Привязать события к session/card/cadet, сохранить серверные timestamps и порядок, не дублировать последнюю карточку, которая присутствует одновременно в текущем состоянии и архиве. Для схемы допускается согласованное поле `sessions[].actions`; новые тесты используют его. При другой структуре документировать контракт и адаптировать только форму тестового входа, не ослабляя проверки поведения.
- Добавлять в prompt только разрешённые данные, а не весь `dynamic_state`/`incoming_card`. Сведения заявителя не должны попасть в отчёт. Безопасные поля действий — kind/service/status/card_id/server at; свободный текст действий рассматривать как недоверенные данные и применять существующую политику защиты персональных данных. Описание действий отделять от установленной ошибки: факт смены статуса сам по себе не означает правильность.
- Допускать описательный анализ при наличии содержательных сохранённых действий, даже без оценки. Явно говорить «оценивание не проводилось / корректность не установлена»; не присваивать баллы и не интерпретировать `ungraded`, `is_passed=False`, `errors_count=0` как оценённый провал/успех. Полностью пустой снимок и пустая ungraded-заглушка должны давать честный `insufficient_data` до LLM вызова.
- Нормально обрабатывать остановленное преподавателем занятие: его сессии закрыты технически, но незаконченная карточка остаётся незаконченной в содержании отчёта. Legacy DDS и действительные сохранённые оценки продолжить поддерживать.
- Исправить/документировать локальное соединение backend ↔ отдельный LLM без открытия внешнего интернета. Подготовить конкретную конфигурацию сети/адреса и read-only health-проверку из backend. Не менять глобальный Docker daemon, не скачивать модели, не печатать секреты, не добавлять внешний fallback. Для runtime smoke использовать только уже имеющуюся локальную модель и синтетические данные, не создавать задания по реальным занятиям. Если runtime не готов, описать конкретный отсутствующий компонент; не объявлять задачу полностью исправленной по одним mock-тестам.
- Проверить явный retry после исправления данных/подключения: новый snapshot, attempt+1, существующие completed jobs без перегенерации, защищённый доступ только ADMIN/владельцу TEACHER. Показать человеку понятную причину недоступности/недостатка данных; менять UI разрешено только в компоненте отчёта преподавателя при необходимости.

## Область и ограничения

Основная область: `backend/core/dds_report_data.py`, `dds_report_llm.py`, `dds_report_jobs.py`, `backend/api/router_dds_reports.py`; локальная compose/runtime документация; связанные report tests. При необходимости `frontend_react/components/teacher/dds-lesson-report.tsx` и его тесты.

Запрещено менять frontend занятия оператора ДДС, форму карточки, действия служб, механику очереди/сохранения, таймеры, режим экзамена, подсчёт оценок и другие исправления тестировщика. Не запускать миграции на рабочей БД, не менять чужой dirty tree, не делать commit/push/deploy. Новая нейрооценка карточек и эталонов не входит в задачу.
