# FIX-05 — одинаковые билеты с разными идентификаторами

Исполнитель: отдельный Gemini worker `fix05_generation`. Только после команды пользователя.

## Установлено и что ещё неизвестно

Ранее исправлено удвоение каталога: GeneratedTicket и ScenarioTicket с одним ID
являются двумя представлениями одного билета. Не удалять эти зеркала.
Текущий генератор шаблонный; фоновой задаче передаётся один Faker на пакет,
UUID создаётся заново. Проверки одинакового содержимого разных UUID при записи нет.
Без ID конкретных пар и трассы запросов причина именно тестерских пар не доказана.
Не объявлять автоматически, что старый merge-баг вернулся или виновата LLM.

## Работа

1. Проследить POST generate → background task → генератор → две таблицы → список.
   Различать двойной запрос/повтор задачи, одинаковый ID в двух форматах и разные UUID
   с одинаковыми фабулой, фактами, эталоном и службами.
2. Гарантировать уникальные упражнения внутри одного пакета; fingerprint не включает
   ID, sequence number и время. Одинаковая фабула с разными существенными фактами допустима.
3. Коллизия повторяет генерацию с ограниченным числом попыток. Не зависать бесконечно;
   при исчерпании честно сообщать фактический результат, не показывать запрошенное N как готовое.
4. Сохранить зеркала, approvals, фильтры и старые данные; существующие дубликаты не удалять.
   Не вводить глобальный запрет одинакового текста во всех исторических занятиях.

Scope: `backend/api/router_tickets.py` (генерация), `backend/core/ticket_generator.py`,
при необходимости generation UX в teacher/tickets; не трогать массовое approve FIX-04.

Готов контракт `tests/test_tester_generation_duplicates.py`: A,A,B при count=2;
контроль одинаковой фабулы при разных фактах; оба API-пути и сохранение зеркал.
