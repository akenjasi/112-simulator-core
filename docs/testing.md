# Проверки проекта

Статус: действующий интерфейс запуска. Состав проверок задают manifests и workflow; не копируйте сюда постоянно меняющиеся количества тестов.

## Среда и изоляция

CI/Docker используют Python3.11, frontend — Node22/npm. Установите runtime через --require-hashes из backend/requirements/runtime.lock и frontend package-lock, тестовый инструментарий из backend/requirements/test.txt. ML-зависимости могут требовать отдельной установки, как в существующем workflow. Версии этой уборкой не обновляются. Все четыре Python-манифеста собраны в backend/requirements.

`tools/quality/verify.sh` создаёт собственную SQLite/token proof до импорта backend и удаляет только свои ресурсы. Унаследованный непустой DATABASE_URL запрещён. Не обходите эту защиту адресом рабочей БД. Pytest backend/tests/conftest.py тоже проверяет изоляцию; исторические тесты в отличие от runner могут иметь другие внешние требования.

Общий вход — `make test`; `make test-all` дополнительно выполняет полный backend suite. Даже при отказе одного независимого набора Makefile выполняет остальные наборы и возвращает ненулевой итог. Точечные команды из корня проекта:

```bash
bash tools/quality/verify.sh backend-core
bash tools/quality/verify.sh frontend
bash tools/quality/verify.sh all
bash tools/quality/verify.sh backend-all
python -m pytest -c tools/tests/acceptance/pytest.ini tools/tests/acceptance -q
python -m unittest discover -s docker/offline/tests -p 'test_offline_*.py' -v
python -m unittest discover -s tools/tests/utilities -v
python backend/tests/postgres/check_queue.py
```

| Режим runner | Что проверяет |
|---|---|
| backend-core | tools/quality/checks/backend-core.txt |
| frontend | frontend manifest, Vitest, tsc, static production export |
| all | backend-core и frontend; это режим по умолчанию |
| backend-all | Все backend/tests/: полный набор, включая актуализированные legacy-контракты |

Reports/summary.json сохраняются в data/checks/verification либо IMBA_VERIFY_REPORT_DIR. Проверка manifests выполняется до выделения ресурсов. Runner не принимает недостающий файл как успешно пропущенную стадию и не изменяет список при падении.

## Независимые и целевые проверки

`tools/tests/acceptance` имеет отдельную pytest.ini, чтобы проверка runner не импортировала его изолирующий tests/conftest. Независимые tests/acceptance manifests не меняют ради зелёного результата. [Правила приёмки](../tools/tests/acceptance/README.md).

- DDS queue/saved tickets/cycle/service policy: backend/tests/test_dds_queue.py и связанные наборы из backend manifest. PG-скрипт создаёт собственный PostgreSQL15 container и проверяет реальные конкурирующие транзакции.
- Немедленный автоматический разбор: backend/tests/test_dds_phone_v2.py проходит самостоятельный старт → полный телефонный цикл → результат без преподавательских баллов; проверяет позднее подтверждение, исправления, неточную сохранённую запись, остановку, изоляцию карточек/пользователей и отсутствие изменения истории при чтении. frontend/tests/student-review.test.tsx проверяет советы без доступной преподавательской оценки, собственные записи входящих докладов и ошибки формата. Эти проверки не запускают языковую модель.
- Student workspace, history и review: backend test_student_workspace.py, frontend student-current-lesson/student-attempt-review наборы. Наличие пяти UI-критериев не заменяет протокол API.
- Экспертное оценивание: backend/tests/test_teacher_grading_acceptance.py и frontend 27_teacher/teacher-grading.acceptance.test.tsx.
- Фоновая очередь отчётов: backend/tests/test_report_scheduler.py проверяет суточный период, права, отсутствие новых данных, перенос старых jobs, восстановление, отмену, stale attempts, retry и CPU/RAM/cgroup на отдельных SQLite. frontend/tests/student-report-queue.test.tsx проверяет состояния обеих ролей и отсутствие POST при чтении.
- Ручная проверка отчётов выполняется на отдельной БД: два студента с разными историями, запрос и повторное нажатие, ошибка и повтор, завершение урока преподавателем, ожидание CPU/RAM, запуск урока во время генерации и повторное чтение готового текста. Сверяйте job_id/attempt/updated_at до и после чтения, состояние слота LLM и сон runtime. Проверяйте московский период и фактическую часть отдельно от качества советов модели; стендовые пороги не переносите в рабочий backend.
- Нейроотчёты: tests/test_dds_report_{data,jobs,llm}_{acceptance,unit}.py и frontend dds-lesson-report tests. Controlled LLM responses/отказы не являются live inference.
- Scope guard рабочего DDS использует docs/dds-workflow-frontend-baseline.json. Первоначальная карта sha256 сохранена; approved_updates закрепляет точные хеши уже интегрированных изменений и исправления жизненного цикла уведомлений. У каждой записи есть основание и исходная ревизия. Произвольные изменения, добавления и удаления по-прежнему отклоняются; это проверяют отрицательные probes. Новое согласованное изменение требует отдельного рассмотрения, а не замены всей карты.
- Offline checks используют recording Docker/curl fakes и временные файлы, не настоящие images/weights/live DB. Отдельная проверка утилит имитирует TTS/копирование моделей; не запускает seeder для реальной БД.

Исторические исходы проверок сохранены в [истории](history/README.md). Не превращайте старый SUCCESS/красный тест в текущее состояние без повторного запуска.

## CI и границы доказательства

`.github/workflows/quality.yml` устанавливает backend/frontend dependencies и запускает backend-core и backend-all, offline contracts, проверки утилит/Makefile, frontend и независимые tests. GitHub branch protection задаётся вне репозитория; конфигурация workflow не доказывает, что удалённый run прошёл.

После перемещения файлов проверьте imports, scripts, Docker/packaging paths, локальные Markdown links и `git diff --check`. При изменении frontend routes выполняйте tsc на чистом generated state и production export. Не подавляйте Vitest unhandled errors.

Core остаётся быстрым минимальным контуром; backend-all обязателен в CI. Старые имена тестов не означают поддержку прежних обходов авторизации, синтетических ответов ML или удалённых API. Неподключённый runtime проверяется на явный отказ; модельный unit test использует явную заглушку и не выдаётся за inference.

Реальные speech/SIP/LDAPS/GPU, RPO/RTO, нагрузка, mobile и нормативные требования принимаются отдельно; остаточные работы собраны в [backlog](backlog.md).

## Приёмка немедленных персональных рекомендаций на GPU

Регрессии преподавательского разбора покрыты `backend/tests/test_teacher_demo_review.py`, `frontend/tests/27_teacher/teacher-demo-fixes.test.tsx` и `teacher-demo-report.test.tsx`: сохранение выбора при оценке, согласованное запрещение оценки несданной карточки, первичное оценивание/пересмотр, реальный протокол вместо служебных «несоответствий» и явный запуск прежней memory_low-задачи после включения деморежима. Чтение отчётов по-прежнему не запускает модель. Для CPU-проверки можно явно использовать меньшую установленную модель по инструкции инференса; это не заменяет отдельную GPU-приёмку.

Автоматизированные проверки реализации: `backend/tests/test_demo_reports.py`, `frontend/tests/student-review.test.tsx` и `frontend/tests/student-report-queue.test.tsx`.

Эта процедура выполняется отдельно на демостенде. Автотесты с управляемым ответом проверяют жизненный цикл, права и формат, но не подтверждают качество модели, использование GPU или время ответа.

### Подготовка

1. Используйте отдельную тестовую БД и подготовленные билеты с телефонным циклом. Нужны преподаватель, два курсанта его группы, посторонний курсант и посторонний преподаватель. Рабочие данные не заменяйте и не очищайте.
2. Включите `DDS_REPORT_MODE=demo` в окружении backend и примените конфигурацию по [инструкции инференса](operations/inference.md#включение-немедленного-деморежима). Для контейнерного стенда выберите `LLM_RUNTIME=gpu`; модель и драйверы должны быть подготовлены заранее.
3. Убедитесь, что `/health` inference доступен. Запишите модель, квантование, GPU/VRAM, число слотов, таймаут, версию приложения. Наличие HTTP health не доказывает работу на GPU: сохраните строки журнала offload и снимок использования VRAM во время реальной генерации.
4. Откройте два отдельных браузерных профиля курсантов и профиль преподавателя. Записывайте время завершения занятия и появления каждого готового ответа; универсальный норматив скорости пока не задан.

### Самотренировка

1. Курсант выбирает подготовленный билет, выполняет полный телефонный цикл и закрывает последнюю карточку.
2. Без кнопки «Сформировать» и без выставления баллов появляется «ИИ анализирует занятие», затем текст рекомендаций на рабочем месте. Откройте тот же результат в разборе и истории кабинета.
3. Сверьте пять критериев, ошибки и исправления с протоколом. Успешному прохождению модель не должна приписывать ошибки; допустим совет о следующей более сложной тренировке.
4. Перезагрузите страницу и повторно откройте разбор. Текст, ID отчёта, attempt и snapshot_at должны сохраниться; нового запроса генерации в inference нет.

### Занятие с преподавателем

1. Преподаватель назначает группе два билета и запускает занятие. Первый курсант проходит без ошибок. Второй допускает неверный этап и исправляет его, сохраняет неточную запись доклада; одну карточку оставляет незавершённой. Для проверки просрочки проведите отдельную попытку с первичным подтверждением позднее 30 секунд.
2. Первый курсант завершает свою работу раньше. Персональный текст пока не генерируется: показано ожидание завершения всего занятия.
3. Преподаватель завершает занятие, не выставляя оценки. Автоматически запускаются общий отчёт и отдельные рекомендации каждому курсанту. Не нажимайте «Сформировать» и не ждите наступления нового дня.
4. В кабинете/разборе каждый курсант видит только собственный результат; преподаватель сразу видит ход анализа и оба персональных результата на экране мониторинга после завершения урока. Тот же блок доступен в истории завершённого занятия. Советы первому не содержат ошибок второго. Второму сохраняются различия между исправленной ошибкой, неточной записью и незавершённостью.
5. Повторите завершение занятия. Число отчётов и запросов к модели не увеличивается; личные тексты не перезаписываются.

### Проверка качества каждого реального ответа

- Числа и статусы совпадают с протоколом; рекомендации относятся к сохранённым затруднениям этого курсанта.
- Невыполненный критерий не называется «ещё не оценённым». Исправление не удаляет прежнюю ошибку из разбора.
- Отсутствие баллов преподавателя не объясняется выдуманной причиной и не блокирует советы. Модель не предлагает числовые баллы по пяти критериям.
- Нет замечаний к психологии, речи или опросу заявителя. Советы конкретны и пригодны для следующей тренировки.
- При неполном прохождении явно видна незавершённость, без придуманного числового провала. При отсутствии протокола видны ограничения данных.
- Невалидный JSON/неизвестная ссылка на основание/оборванный ответ не показывается как готовая рекомендация; появляется ошибка и явный повтор. Полную смысловую корректность JSON-проверка не гарантирует.

### Отказы, перезапуск и права

1. На отдельном тестовом inference остановите сервис и завершите самотренировку. Занятие должно остаться завершённым с сохранёнными действиями, а рекомендации перейти в ошибку. Восстановите inference, нажмите «Повторить анализ ИИ»: попытка увеличивается один раз, текст появляется. Двойное нажатие не дублирует генерацию.
2. Перезапустите тестовый backend во время генерации. После запуска состояние — ошибка с возможностью явного повтора; завершённое занятие и замороженный снимок сохранены. Ранее готовые тексты остаются доступными.
3. Через авторизованные API-запросы проверьте GET/POST `/api/ai-analytics/sessions/{session_id}/recommendation` для чужого курсанта и постороннего преподавателя — 403. Без входа — 401. CADET не получает GET `/api/ai-analytics/lessons/{lesson_id}/personal-reports` — 403. Преподавателю разрешено только собственное занятие. Адреса проверяют на тестовом стенде, без передачи чужих токенов в скриншоты/отчёт.
4. Верните `DDS_REPORT_MODE=queued`, перезапустите backend и проведите отдельную попытку. Немедленная персональная генерация не запускается, обычная фоновая очередь сохраняет прежнее поведение.

Приёмка завершена, когда записаны сценарий, ожидаемые/фактические результаты, ID сессий и отчётов, снимки интерфейса, время каждого ответа и свидетельство GPU. Качество и скорость фиксируются по реальному выводу модели; успех unit/интеграционных тестов не заменяет этот протокол.
