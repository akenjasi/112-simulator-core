# Тестовая инфраструктура и запуск проверок (P2)

Документ описывает единый интерфейс запуска проверок, изоляцию тестовых окружений и защиту прикладных баз данных.

## 1. Единый интерфейс запуска: `scripts/verify_build.sh`

Точка входа для запуска верификации проекта — скрипт `scripts/verify_build.sh`. Скрипт корректно определяет корень репозитория независимо от текущей рабочей директории (`cwd`).

### Режимы работы

| Режим | Описание | Состав стадий |
|---|---|---|
| `backend-core` | Критические тесты бэкенда по зафиксированному манифесту | `backend-core` |
| `backend-all` | Диагностический запуск всех тестов в `tests/` | `backend-all` |
| `frontend` | Обязательные фронтенд-проверки | `frontend-tests`, `typecheck`, `frontend-build` |
| `all` (по умолчанию) | Полный цикл верификации | `backend-core`, `frontend-tests`, `typecheck`, `frontend-build` |

Запуск:
```bash
# Критический backend-набор (режим по умолчанию для быстрой приёмки бэкенда)
bash scripts/verify_build.sh backend-core

# Полный цикл
bash scripts/verify_build.sh all
# или просто:
bash scripts/verify_build.sh
```

## 2. Манифесты проверок (`scripts/checks/`)

Состав критических проверок зафиксирован в манифестах:
- `scripts/checks/backend-core.txt`: список критических файлов тестов бэкенда.
- `scripts/checks/frontend-core.txt`: список критических тестов фронтенда.

Правила обработки манифестов:
- Пустые строки и строки, начинающиеся с `#`, игнорируются.
- Проверка наличия всех файлов из манифеста выполняется **до** выделения тестовых ресурсов и запуска тестов. Если хотя бы один файл отсутствует, runner завершается с ошибкой (`exit 1`).

## 3. Изоляция тестовой базы данных и Guard прямого запуска

### Защита от повреждения прикладных данных
Ни штатный runner `scripts/verify_build.sh`, ни прямой запуск `pytest` не подключаются к рабочей или внешней базе данных:

1. **Запрет унаследованного `DATABASE_URL` в runner:**
   При запуске `scripts/verify_build.sh` при наличии установленной переменной `DATABASE_URL` runner немедленно завершает работу с ошибкой:
   ```
   ERROR: Inherited external DATABASE_URL is not allowed. Runner must allocate its own isolated database.
   ```
2. **Изолированное окружение на каждый запуск:**
   Для каждого запуска создаётся уникальный временный каталог (`mktemp -d /tmp/imba_verify_XXXXXX`), в котором размещается свежая временная база данных SQLite (`test.sqlite`).
3. **Механизм подтверждения владения ресурсом (Ownership Token) и защита от симлинков:**
   - Runner генерирует уникальный криптографический токен (UUID4) и записывает его в файл `.token` внутри приватного временного каталога базы данных.
   - Переменная окружения `IMBA_TEST_TOKEN` передаётся дочернему процессу `pytest`.
   - В `tests/conftest.py` до импорта модулей `backend.database` или `backend.main` выполняется строгая проверка безопасности:
     - Путь к файлу БД не должен являться симлинком (`db_path.is_symlink()`);
     - Родительский каталог БД и все его компоненты не должны содержать симлинков (`os.path.realpath(db_dir) == db_dir`);
     - Файл `.token` должен быть регулярным файлом в каталоге БД и не являться симлинком;
     - Файл БД не должен существовать до первой инициализации тестового окружения (любой существующий файл или ссылка, включая hardlink и symlink, отклоняется);
     - Токен из переменной окружения `IMBA_TEST_TOKEN` должен строго совпадать с содержимым файла `.token`.
   - Если токен отсутствует, файл `.token` не найден, обнаружен симлинк, файл БД уже существует или токен не совпадает, выполнение немедленно прерывается с ошибкой (`exit 1`) до создания SQLAlchemy engine и любых операций с БД.
   - Произвольные PostgreSQL-адреса и относительные пути на этом этапе отклоняются.
4. **Безопасный прямой запуск `pytest`:**
   При прямом вызове `python -m pytest` без предварительно настроенного окружения `tests/conftest.py` автоматически создаёт изолированный временный каталог, приватную SQLite БД и токен владения. По завершении сессии временные файлы автоматически удаляются.
5. **Изоляция секретов и доверенная передача через `.secret`:**
   - Runner генерирует уникальный криптографический ключ и сохраняет его в доверенный файл `.secret` в каталоге БД рядом с `.token`.
   - `tests/conftest.py` доверяет переданному `SECRET_KEY` только при совпадении с содержимым регулярного файла `.secret`.
   - При прямом запуске `pytest` или при отсутствии криптографического подтверждения через `.secret` любой внешний `SECRET_KEY` безусловно перезаписывается свежесгенерированным случайным значением (`secrets.token_hex(32)`).
   - Прикладной `.env` не считывается, а параметры `HF_HUB_OFFLINE="1"` и `TRANSFORMERS_OFFLINE="1"` предотвращают обращение к внешним ML-ресурсам.

## 4. Очистка ресурсов и завершение процессов (Process Tree Cleanup)

- В `scripts/verify_build.sh` установлен обработчик сигналов `trap` (`EXIT`, `INT`, `TERM`).
- Стадии runner-а выполняются в собственных группах процессов (`set -m`), а команды этапов используют `exec` для прямой подмены оболочки.
- При получении сигналов прерывания (SIGINT/SIGTERM) или выходе runner вызывает `stop_child_tree()`:
  - Рекурсивно собирает идентификаторы всех потомков этапа (`pgrep -P`);
  - Отправляет сигнал `SIGTERM` в группу процессов и всем дочерним процессам;
  - Ожидает штатного завершения до 5 секунд с постоянной проверкой живучести процессов;
  - В случае зависания эскалирует завершение до `SIGKILL`;
  - Не использует неизбирательные глобальные команды вроде `pkill`, изолируя воздействие только на собственный процессный граф.
- Удаление временного каталога базы данных (`rm -rf ${RUN_TEMP_DIR}`) происходит **строго после** полного завершения всех процессов поддерева, что исключает ошибки I/O и зомби-процессы.
- Каталог отчёта сохраняется вне удаляемой базы данных и не затрагивает внешние файлы.

## 5. Структура отчётов (Summary и логи)

Каталог отчёта определяется переменной `IMBA_VERIFY_REPORT_DIR`. Если переменная не задана, создаётся директория вида:
`reports/verification/<YYYYMMDD_HHMMSS>_<unique_id>/`

### Файлы отчёта:
- `<stage>.log`: полный вывод stdout/stderr соответствующей стадии (например, `backend-core.log`).
- `summary.json`: структурированный JSON с результатами выполнения:

```json
{
  "mode": "backend-core",
  "status": "passed",
  "stages": [
    {
      "name": "backend-core",
      "status": "passed",
      "exit_code": 0
    }
  ]
}
```

В случае падения стадии последующие стадии помечаются со статусом `skipped` и `exit_code: null`, а общие логи не содержат конфиденциальных токенов или паролей к БД.
