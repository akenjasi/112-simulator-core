# ТЗ 63: Fullstack — Интерактивный диалог (Voicebot Loop: GigaAM -> SLM -> Audio)

**Роль:** Backend & AI Developer / Frontend
**Контекст:** Тренажер не должен быть просто статической формой. Мы делаем интерактивного "виртуального заявителя". Курсант говорит голосом, система его понимает, решает, что ответить, и проигрывает нужную реплику заявителя. Эта логика должна работать в браузере (наушники) сейчас, и быть готовой для работы через SIP-телефон в будущем.

## Задача 1: Backend — Пайплайн диалога
В созданном тобой WebSocket-эндпоинте для ASR (`/api/v2/asr/stream`) необходимо выстроить полный цикл:
1. **ASR (Распознавание):** Как только из аудиочанка от оператора распознана цельная фраза (например, *"Служба 112, что у вас случилось?"*).
2. **SLM / NLU Классификатор (Понимание):**
   - Распознанный текст передается в классификатор намерений (Intent Classifier).
   - *Для MVP:* Напиши заглушку (или простую функцию на регулярках / эмбеддингах). Например, если в тексте есть "что случилось" -> Intent = `ASK_WHAT_HAPPENED`. Если есть "адрес" -> Intent = `ASK_ADDRESS`.
3. **Скрипт ответа (Сценарий):**
   - На основе Intent и текущего состояния билета (State Machine), система выбирает следующий аудио-ответ заявителя.
   - Например, на `ASK_WHAT_HAPPENED` система должна ответить файлом `caller_fire_panic.wav` (где заявитель кричит о пожаре).
4. **Команда на воспроизведение:**
   - Бэкенд отправляет по WebSocket на фронтенд команду: 
     `{"event": "PLAY_AUDIO", "file_url": "/media/scenarios/ticket_1/caller_fire_panic.wav", "text_transcript": "Горим! Пожар на Ясном проезде!"}`

## Задача 2: Frontend — Воспроизведение и Синхронизация
Фронтенд выступает "плеером" для виртуального заявителя (пока мы не подключили реальную АТС).
1. Когда по WebSocket приходит событие `PLAY_AUDIO`:
   - Фронтенд должен создать объект `Audio` (или использовать `audioContext`) и проиграть указанный файл в наушниках курсанта.
   - Во время проигрывания аудио (пока виртуальный заявитель "говорит"), микрофон оператора может либо приглушаться (чтобы не распознавать эхо), либо фронтенд блокирует отправку чанков на ASR до конца аудио.
2. Текст ответа (`text_transcript`) должен отобразиться в UI, чтобы преподаватель (или сам оператор при разборе полетов) видел, что именно ответил бот. (Опционально: можно показывать субтитры для дебага).

## Архитектурная готовность к IP-телефону (Asterisk)
*Примечание для разработчика:* В будущем фронтенд не будет играть аудио напрямую! Бэкенд вместо отправки `PLAY_AUDIO` на фронтенд будет делать API-запрос к Asterisk: *"Проиграй этот WAV-файл в канал SIP-телефона"*. 
Поэтому **строго отделяй** логику принятия решений (Стейт-машина диалога) от логики воспроизведения звука. Бэкенд должен просто генерировать "Ответное действие", которое в текущем MVP исполняет браузер, а в проде будет исполнять АТС.
